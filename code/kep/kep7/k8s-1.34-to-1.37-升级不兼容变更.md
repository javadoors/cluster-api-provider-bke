# Kubernetes 1.34 → 1.37 不兼容变更与升级指南

> 数据来源：
> - 官方 API 弃用指南 https://kubernetes.io/docs/reference/using-api/deprecation-guide/
> - 各版本 CHANGELOG 中的 `Urgent Upgrade Notes` / `Deprecation` / `API Change` 章节
> - 版本偏差策略 https://kubernetes.io/releases/version-skew-policy/

> 说明：官方弃用指南中“按版本移除的 API”目前最新只到 v1.32（flowcontrol v1beta3），因此 1.34–1.37 期间**没有**内置资源组版本的批量移除。此窗口内的变更主要集中在 feature-gate 收紧、Flags/字段移除、指标重命名、默认行为改变，以及 alpha/beta API 迁移（DRA、Workload/PodGroup、StorageVersionMigration、PodCertificate 等）。

## 摘要（总结性不兼容变更）

### 1. 组件启动失败类（升级前必须清理 Flags）
- kubelet：`--cloud-config`（1.34）、`--register-schedulable`（1.34）、`--pod-infra-container-image`（1.35）。
- kubelet 内嵌 cAdvisor：一批已弃用 cAdvisor Flags 被移除，设置任一即启动失败（1.37）。
- 节点运行环境：cgroup v1 被弃用，`failCgroupV1` 默认 true（1.35）。

### 2. API 对象移除（升级前必须删除对应资源）
- DRA：`resource.k8s.io/v1alpha3`（仅留 DeviceTaintRule）、kubelet gRPC `v1alpha4`、`admin-access` 标签改名（1.34）。
- `StorageVersionMigration v1alpha1`（1.35）。
- `scheduling.k8s.io` Workload/PodGroup：`v1alpha1` 移除（1.36）→ `v1alpha2` 移除（1.37）。
- `SnapshotMetadataService v1alpha1`（1.36）。
- PodCertificateRequest：`PKIXPublicKey`/`ProofOfPossession` 字段移除（1.37）。

### 3. 依赖第三方集成改造
- 客户端：gogo/protobuf 移除（1.34 起）、REST client API streaming 移除（1.34）。
- Scheduler 插件：PreFilter 接收 NodeInfo（1.34）、PreBind 返回 `PreBindPreFlightResult`（1.36）。
- DRA driver：细粒度 RBAC 权限（1.36）。

### 4. 指标重命名 / 标签拆解（影响监控告警）
- 大量 apiserver/etcd 指标 label 拆分为 `group`+`resource`（1.34）。
- `scheduler_scheduler_cache_size`、`apiserver_encryption_config_controller_automatic_reload_*`（1.34）。
- `etcd_bookmark_counts`→`etcd_bookmark_total`、`volume_operation_total_errors`→`volume_operation_errors_total`（1.36）。

### 5. 默认行为改变（高风险）
- `SELinuxMount` GA（1.37，SELinux 集群可能破坏工作负载）。
- kubelet `eventRecordQPS=0` 变为不限流（1.37）。
- kube-proxy 向 nftables 过渡，`ipvs` 弃用（1.35/1.37）。
- kubeadm 移除 flex-volumes 内置支持（1.36）。
- `git-repo` volume 插件禁用（1.36）。

## 一、v1.34（从 1.33 升级）

### 必须处理（会直接导致失败/行为改变）

- **kubelet 移除 `--cloud-config` 标志**：配置了该标志会导致启动失败。
- **kubelet 移除 `--register-schedulable` 标志**。
- **移除 `LegacySidecarContainers` feature gate**（彻底移除）。
- **移除 `DevicePluginCDIDevices`、`PodDisruptionConditions` 等已 GA 的 feature gate**。
- **DRA API 迁移/清理**：
  - 删除 kubelet gRPC `v1alpha4` API（DRA driver 应使用 v1beta1 helper）。
  - `resource.k8s.io/v1alpha3` 仅保留 `DeviceTaintRule`，其余类型移除；升级前需删除 `<1.32` 存储的 resourceclaims / resourceclaimtemplates / deviceclasses / resourceslices 对象。
  - `admin-access` 标签由 `resource.k8s.io/admin-access` 改为 `resource.kubernetes.io/admin-access`。
- **移除 gogo/protobuf**：`cri-api`、`kubelet/pkg/apis/deviceplugin`、`podresources`、`kms/apis`、`externaljwt`、`pluginregistration` 等包中已弃用的 gogo 协议定义被移除。
- **移除 REST 客户端 API streaming**：typed / dynamic / metadata client 的 `List()` streaming 支持，以及 `kubernetes.io/initial-events-list-blueprint` 注解。
- **指标重命名与标签拆解**：
  - `apiserver_encryption_config_controller_automatic_reload_success_total` / `_failure_total` → `apiserver_encryption_config_controller_automatic_reloads_total`。
  - `scheduler_scheduler_cache_size` → `scheduler_cache_size`。
  - apiserver/etcd 大量指标 label 由 `resource`/`type`/`kind` 拆为 `group` + `resource`（见 CHANGELOG #131845）。

### 弃用

- kubeconfig `preferences` 字段弃用，改用 `kuberc`。
- DRA kubelet gRPC 毕业到 v1，v1beta1 弃用。

## 二、v1.35（从 1.34 升级）

### 必须处理

- **kubelet 移除 `--pod-infra-container-image` 标志**：
  - 非 kubeadm 集群需先从 kubelet 配置中删除，否则启动失败。
  - kubeadm 集群若在 `extraArgs` 中传入，需手动删除（init/join 不会自动清理）。
- **cgroup v1 弃用（`failCgroupV1` 默认 true）**：
  - kubelet ≥1.35 在 cgroup v1 主机上默认无法启动。
  - kubeadm preflight 对 cgroup v1 直接报错（SystemVerification）；可通过 `failCgroupV1: false` 或忽略 preflight 规避。
- **kube-proxy `ipvs` 模式弃用**：建议迁移 nftables（新内核）/ iptables（旧内核）。
- **`StorageVersionMigration` 移除 `v1alpha1`，仅保留 `v1beta1`**：升级前必须删除所有 v1alpha1 对象。
- **移除 `StrictCostEnforcementForVAP`、`StrictCostEnforcementForWebhooks` feature gate**（自 v1.32 起已锁定）。
- **Go API 类型移除 gogo/protobuf**：不再默认实现 `ProtoMessage()`。可用构建标签 `kubernetes_protomessage_one_more_release` 暂缓一个版本，但 1.36 起彻底移除。
- **Pod resize 仅允许 CPU/内存**，其他资源类型被禁止。
- **`Partitionable Devices`（alpha）向后不兼容**：1.34↔1.35 之间升级/降级前需删除使用该特性的 ResourceSlice。
- **Service `trafficDistribution=PreferClose` 弃用**，改用 `PreferSameZone`。

## 三、v1.36（从 1.35 升级）

### 必须处理（ACTION REQUIRED）

- **kubeadm 移除对 flex-volumes 的内置支持**：
  - 继续使用需自定义非 distroless 的 KCM 镜像，传 `--flex-volume-plugin-dir`，并用 `extraVolumes` 挂载 `/usr/libexec/kubernetes/kubelet-plugins/volume/exec`。
  - 升级前若不处理，该功能失效。
- **DRA 细粒度 RBAC（`DRAResourceClaimGranularStatusAuthorization` beta 默认开启）**：
  - scheduler / controller 需要 `resourceclaims/binding` 的 update/patch 权限。
  - DRA driver 需要 `resourceclaims/driver` 的 `associated-node:update` 或 `arbitrary-node:update`（或 patch 等价），并按具体 `resourceNames` 限制。
- **指标重命名**：
  - `etcd_bookmark_counts` → `etcd_bookmark_total`。
  - `volume_operation_total_errors` → `volume_operation_errors_total`。
  - 需同步更新自定义监控大盘与告警规则。
- **Scheduler PreBind 插件并行化**：插件需将 `PreBindPreFlight` 改为返回 `PreBindPreFlightResult`；返回 nil 保持串行行为。

### API 移除 / 弃用

- **`scheduling.k8s.io/v1alpha1` Workload API 移除**，替换为 `v1alpha2`。
- **`SnapshotMetadataService` 移除 `v1alpha1`，升 `v1beta1`**。
- **gogo `ProtoMessage` 构建标签彻底删除**。
- **Service `.spec.externalIPs` 弃用告警**。
- **`git-repo` volume 插件默认禁用且无法再开启**。
- **`metav1.FieldsV1.Raw` 直读弃用**，改用 `NewFieldsV1` / `GetRawBytes` / `GetRawString` / `SetRawBytes`。
- **Pod Certificates**：`pkixPublicKey` / `proofOfPossession` 弃用，改用 `stubPKCS10Request`。
- `sets.String` → `sets.Set[string]`：对 `NewLifecycle` 函数消费者是 breaking change。

## 四、v1.37（从 1.36 升级）

### 必须处理（ACTION REQUIRED）

- **`SELinuxMount` 毕业 GA（默认开启）**：
  - 对启用 SELinux 的集群可能破坏现有工作负载。
  - 升级前按官方博客排查/修复，或选择退出：https://kubernetes.io/blog/2026/04/22/breaking-changes-in-selinux-volume-labeling/
  - 未启用 SELinux 的集群可忽略。
- **`DisruptionMode` 由枚举改为结构体；`scheduling.k8s.io` 从 `v1alpha2` 升 `v1alpha3` 并彻底丢弃 `v1alpha2`**：
  - 升级前必须删除所有 v1alpha2 对象。
- **kubelet `eventRecordQPS=0` 现表示不限流**（与文档对齐）：
  - 依赖旧默认限流行为者需显式设置非 0 值（例如 50）。
- **kubelet 默认记录生效配置到日志**：需限制 `nodes/logs` ClusterRole 仅授予可信用户。

### API 移除 / 弃用 / 行为变化

- **PodCertificateRequest 毕业 GA**：`PKIXPublicKey`、`ProofOfPossession` 字段从 v1 API 移除，升级前更新客户端。
- **kubelet 内嵌 cAdvisor 切换为精简模块（`github.com/google/cadvisor/lib`）**：
  - 一批已弃用 cAdvisor Flags 被移除，设置任一导致 kubelet 启动失败（仅保留 `--housekeeping-interval`）：`--application-metrics-count-limit`、`--boot-id-file`、`--container-hints`、`--containerd`、`--containerd-namespace`、`--enable-load-reader`、`--event-storage-age-limit`、`--event-storage-event-limit`、`--global-housekeeping-interval`、`--log-cadvisor-usage`、`--machine-id-file`、`--storage-driver-*` 系列。
  - `userDefinedMetrics` 及 `container_cpu_load_average_10s`、`container_cpu_load_d_average_10s`、`container_tasks_state` 等指标不再导出。
- **kube-proxy 向 nftables 过渡**：
  - kubeadm 在未提供 `KubeProxyConfiguration` 或 mode 为空时显式设为 iptables。
  - 未显式设置 mode 会有告警；ipvs 自 v1.35 起弃用。
- `kubectl run -f/--filename` 弃用（此前即被忽略）。
- `DeclarativeValidationTakeover` feature gate 锁定为默认值，不可再设置。
- `NodeSyncPeriod` 从 `KubeCloudSharedConfiguration` 迁移至 `CloudControllerManagerConfiguration.NodeLifecycleController.NodeMonitorPeriod`。
- 默认 etcd 升到 `v3.7.0`；grpc 升 `v1.82.1`（移除 `GRPC_GO_EXPERIMENTAL_DISABLE_STRICT_PATH_CHECKING`）；构建使用 Go 1.26。

## 五、升级实施建议

### 1. 组件升级顺序（官方 version-skew）

1. **kube-apiserver**（HA 集群新旧版本间最多相差 1 个小版本；不允许跳小版本）。
2. **kube-controller-manager / kube-scheduler / cloud-controller-manager**（不得新于 apiserver，可滞后 1 个小版本）。
3. **kubelet**（逐节点 drain；不得新于 apiserver，可滞后 3 个小版本）。
4. **kube-proxy**（不得新于 apiserver，可滞后 3 个小版本）。

### 2. 升级前清单

- [ ] 清理被移除 API 的对象：DRA v1alpha3/v1alpha4、StorageVersionMigration v1alpha1、Workload/PodGroup v1alpha1→v1alpha2→v1alpha3、SnapshotMetadataService v1alpha1（逐级清理）。
- [ ] 清理 kubelet Flags：`--cloud-config`、`--register-schedulable`、`--pod-infra-container-image`、cAdvisor 已弃用 Flags。
- [ ] 处理第三方集成：scheduler 插件（PreBind/PreFilter）、DRA driver RBAC、客户端移除 gogo/protobuf 与 streaming。
- [ ] 更新监控/告警：重命名指标（etcd_bookmark、volume_operation、scheduler_cache_size、automatic_reload 系列）及 apiserver/etcd 标签拆解。
- [ ] 特殊环境单独评估：cgroup v1、SELinux、kube-proxy ipvs、flex-volume。

### 3. 迁移工具

- 使用 `kubectl convert -f <file> --output-version <group>/<version>` 自动转换旧对象（需单独安装 `kubectl-convert` 插件）。
- 升级前可用 `--runtime-config=<group>/<version>=false` 模拟禁用将被移除的 API，验证兼容性。

## 六、k8s 1.34 → 1.37 升级标准方案

### 6.1 升级原则与路径

Kubernetes 官方**不允许控制面跳小版本升级**（apiserver 新旧版本最多相差 1 个小版本）。1.34 → 1.37 跨越 3 个小版本，因此标准方案为**逐小版本升级（3 跳）**：

```
1.34 ──▶ 1.35 ──▶ 1.36 ──▶ 1.37
  Hop 1      Hop 2      Hop 3
```

每个 Hop 都是完整的一次 kubeadm 标准升级，必须完成该版本对应的不兼容变更清理（见本文一/二/三/四节）后才能进入下一跳。

### 6.2 版本偏差约束（全程遵守）

| 组件 | 约束 | 说明 |
|------|------|------|
| kube-apiserver | 逐小版本，不跳级 | HA 集群新旧节点最多差 1 个小版本 |
| kube-controller-manager / kube-scheduler | ≤ apiserver，可滞后 1 个小版本 | 随控制面同步升级 |
| kubelet | ≤ apiserver，可滞后 3 个小版本 | 逐节点 drain 后升级 |
| kube-proxy | ≤ apiserver，可滞后 3 个小版本 | DaemonSet 滚动升级 |
| etcd | 跟随 K8s 推荐版本 | 每个 Hop 配套升级 |

> **铁律**：先升级控制面，后升级 worker；任何时刻 kubelet 不得新于 apiserver。

### 6.3 单跳标准流程（通用模板）

每一跳（如 1.34 → 1.35）都执行以下步骤，全部通过后方可进入下一跳：

```
① 升级前预检（PreCheck）
   ├─ etcd snapshot 备份（etcdctl snapshot save）
   ├─ 集群健康检查（Nodes Ready、Pods Running）
   ├─ 清理本跳将被移除的 API 对象（见 6.4 映射表）
   ├─ 清理本跳将被移除的组件 Flags（见 6.4 映射表）
   └─ kubectl convert / kubectl-convert 迁移存量资源

② 升级控制面（先 master）
   ├─ kubeadm upgrade plan <target>           ← 验证升级计划
   ├─ kubeadm upgrade apply <target>          ← 第一个 master（或单 master）
   ├─ 其余 master：kubeadm upgrade node <target>
   └─ 升级 kubectl/kubeadm 到 <target>

③ 升级 kubelet / kube-proxy（master 节点）
   ├─ 逐 master 节点：kubeadm upgrade node 完成 kubelet 升级
   └─ kube-proxy DaemonSet 滚动升级

④ 升级 worker 节点（逐节点，非阻塞）
   ├─ kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
   ├─ kubeadm upgrade node <target>（升级 kubelet + kubeadm）
   └─ kubectl uncordon <node>

⑤ 升级后验证（PostCheck）
   ├─ kubeadm version / kubectl version 对齐 <target>
   ├─ kubectl get nodes 全部 Ready 且 KubeletVersion 一致
   ├─ 核心组件 Static Pod / Deployment 健康
   └─ 业务应用功能回归 + 监控告警无异常
```

### 6.4 逐跳不兼容变更映射（升级前必须完成）

| 跳 | 目标版本 | 升级前必须处理的关键项 | 参考章节 |
|----|---------|------------------------|---------|
| **Hop 1** | 1.35 | 删除 `--pod-infra-container-image` Flag；cgroup v1 主机处理 `failCgroupV1`（迁移 cgroup v2）；删除 `StorageVersionMigration` v1alpha1 对象（转 v1beta1）；评估 kube-proxy ipvs 弃用；Pod resize 仅 CPU/内存；`trafficDistribution=PreferClose` 改 `PreferSameZone` | 二 |
| **Hop 2** | 1.36 | kubeadm 移除 flex-volume 内置支持（需保留则自定义 KCM 镜像）；清理 Workload/PodGroup v1alpha1、SnapshotMetadataService v1alpha1；DRA driver 补细粒度 RBAC；scheduler PreBind 返回 `PreBindPreFlightResult`；监控指标重命名同步；gogo `ProtoMessage` 构建标签删除 | 三 |
| **Hop 3** | 1.37 | 清理 Workload/PodGroup v1alpha2、PodCertificateRequest 已弃用字段；kubelet 内嵌 cAdvisor 弃用 Flags（仅留 `--housekeeping-interval`）；SELinux 集群评估 `SELinuxMount` GA；显式 `eventRecordQPS`；kube-proxy 显式 mode（iptables/nftables）；`NodeSyncPeriod` 迁移 | 四 |

> **基线说明**：本文起点为 1.34，第一节（v1.34 从 1.33 升级）所列必须处理项（`--cloud-config`、`--register-schedulable`、DRA v1alpha3/v1alpha4、`admin-access` 标签等）应已在集群进入 1.34 时完成。若集群仍残留这些配置，须在 Hop 1 之前补做（见第一节）。

### 6.5 逐跳细化设计

> 每一跳严格按 6.3 通用模板的 ①→⑤ 执行；下面对各跳的差异点（尤其是 PreCheck 和 PostCheck）逐项展开，②③④ 中与模板一致的部分仅在关键字/命令处标注。

#### 6.5.1 Hop 1：1.34 → 1.35

**① 升级前预检（PreCheck）**

```bash
# 1. etcd 快照备份（每个 etcd 节点）
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-1.34-pre-1.35-$(date +%F).db

# 2. 集群健康检查：Nodes 全 Ready，无 CrashLoop/ImagePullBackOff
kubectl get nodes
kubectl get pods -A | grep -vE 'Running|Completed'

# 3. 清理 kubelet Flag：1.35 移除 --pod-infra-container-image
#    （非 kubeadm：直接删 kubelet 配置；kubeadm：清理 ClusterConfiguration/kubelet extraArgs）
grep -rn "pod-infra-container-image" /var/lib/kubelet/config.yaml /etc/kubernetes/ 2>/dev/null
kubectl -n kube-system get cm kubeadm-config -o yaml | grep -n "pod-infra-container-image"

# 4. 删除 StorageVersionMigration v1alpha1 对象（1.35 仅保留 v1beta1）
kubectl get storageversionmigration.storagemigration.k8s.io -o name | xargs -r kubectl delete

# 5. 检查主机 cgroup 版本（1.35 起 kubelet failCgroupV1 默认 true）
stat -fc %T /sys/fs/cgroup      # cgroup2fs=v2；tmpfs=v1（需迁移或 failCgroupV1:false）

# 6. kube-proxy 模式评估（ipvs 自 1.35 弃用）
kubectl -n kube-system get cm kube-proxy -o yaml | grep -A1 "mode:"
```

**② 升级控制面**

```bash
kubeadm upgrade plan v1.35.x      # 校验计划，确认无阻断（cgroup v1 会触发 preflight SystemVerification）
kubeadm upgrade apply v1.35.x     # 单 master；HA 其余 master 见③
# kubeadm 管理的 etcd 随 apply 一并升级（cgroup v1 报错可临时 --ignore-preflight-errors=SystemVerification）
```

**③ kubelet / kube-proxy（master 节点）**

每台 master：升级 kubeadm/kubelet 二进制到 1.35 后 `kubeadm upgrade node` + `systemctl restart kubelet`。

```bash
kubeadm upgrade node
systemctl restart kubelet
```

**④ worker 节点（逐节点，非阻塞）**

```bash
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
# 节点侧：升级 kubeadm/kubelet 到 1.35 → kubeadm upgrade node → restart kubelet
kubeadm upgrade node
kubectl uncordon <node>
```

**⑤ 升级后验证（PostCheck）**

- `kubectl get nodes` 全部 Ready 且 KubeletVersion=v1.35.x。
- cgroup v1 主机：确认 kubelet 正常启动（未设置 `failCgroupV1:false` 则默认拒绝启动）。
- Pod resize：仅 CPU/内存可 resize，其他资源类型请求被拒（通知依赖方）。
- `trafficDistribution=PreferClose` 的 Service 改 `PreferSameZone` 后流量分布符合预期。
- kube-proxy：若暂留 ipvs，记录弃用告警并纳入 Hop 2/3 迁移计划。

#### 6.5.2 Hop 2：1.35 → 1.36

**① 升级前预检（PreCheck）**

```bash
# 1. etcd 快照备份（同上模板）

# 2. flex-volume 使用排查（1.36 kubeadm 移除内置支持）
kubectl get pv -o yaml | grep -B2 "flexVolume\|flex"         # 存量 PV/PVC
```

### 6.6 回滚策略

- **逐跳回滚**：每个 Hop 独立备份 etcd，本跳失败可回退到上一小版本。
- **官方降级限制**：kubeadm 仅支持 `n → n-1` 降级；跨多版本回滚需从 etcd 快照恢复 + 重装目标版本 kubelet。
- **回滚优先级**：etcd 快照恢复 > 控制面降级 > worker 降级。
- **数据风险**：升级窗口期写入的数据在回滚时会丢失，需提前通知业务方。

### 6.7 标准方案执行要点

1. **每跳独立验证**：不跨跳合并操作，上一跳 PostCheck 通过前禁止开始下一跳。
2. **升级窗口规划**：每跳按「控制面 + 全部 worker」估算停机影响，worker 逐节点 drain 会产生业务 Pod 漂移。
3. **非 kubeadm 集群**：本方案以 kubeadm 为标准路径；非 kubeadm 部署需自行映射「控制面二进制替换 + Static Pod 重建」等价步骤，并额外清理 kubelet Flags（1.35 `--pod-infra-container-image` 等）。
4. **声明式升级框架映射**：若通过 openFuyao/CAPBKE 声明式升级，每跳对应一次 `ClusterVersion` Hop（`upgrade-ready` 注解逐跳触发），本节的 PreCheck/PostCheck、逐跳顺序、版本偏差门控均由框架强制执行，见 KEP-8、KEP-7。

## 七、k8s 1.34 直升 1.37 设计方案

### 7.1 背景与目标

第六章标准方案采用「逐小版本、3 跳」升级，全程需人工在每跳之间确认、耗时且窗口长。本章设计**直升方案**：用户通过**一次版本变更操作**（修改 `ClusterVersion.Spec.DesiredVersion`）即完成 1.34 → 1.37，中间无需人工干预。

「直升」在技术实现上存在两个层次，需先区分：

| 层次 | 含义 | 是否受 kubeadm 跳级限制 |
|------|------|------------------------|
| **框架层直升** | 用户一次操作，框架内部自动编排 3 跳 | 否（内部仍逐跳） |
| **kubeadm 层直升** | 一次 `kubeadm upgrade apply 1.37` 跳过 1.35/1.36 | 是（官方不支持） |

### 7.2 可行性分析

#### 7.2.1 kubeadm 跳级限制（关键约束）

- **控制面（apiserver/etcd）**：kubeadm 官方只支持**逐小版本**升级，`upgrade apply` 会校验当前版本与目标版本，**不允许跳过小版本**（1.34 → 1.37 会直接报错）。
- **kubelet / kube-proxy**：版本偏差策略允许滞后 apiserver 至多 3 个小版本。因此 1.37 控制面 + 1.34 kubelet（恰好差 3）在偏差上**勉强合规**，但属于边界值，不推荐长期处于该状态。

> **结论**：kubeadm 层真·单跳不可行；直升方案必须落在**框架层**，由框架在内部把一次操作展开为 3 跳。

#### 7.2.2 存储版本迁移

- apiserver 每个小版本发布时都携带 `storageVersionHash` 与类型注册表，跨版本会触发 apiserver 内部的类型迁移逻辑；跳级时中间版本的「对象注册 / 默认值 / 删除字段」迁移会缺失，导致数据不一致风险。
- 1.35/1.36 分别移除 `StorageVersionMigration v1alpha1`、Workload/PodGroup 等对象，跳级升级需一次性处理 3 个版本的删除，无法复用中间版本的「先迁移后删除」窗口。

#### 7.2.3 API 累积变更

直升意味着 1.35、1.36、1.37 三批不兼容变更（见第六节 6.4 映射表）需在**进入 1.37 前一次性完成**，PreCheck 复杂度显著上升；一旦遗漏，升级后静默失败面更大。

### 7.3 方案设计

#### 7.3.1 方案 A：框架层直升（内部自动 3 跳，推荐）

```
用户操作：修改 ClusterVersion.Spec.DesiredVersion = v2.7.0（含 K8s 1.37）
              │
              ▼
ClusterVersionReconciler 解析 UpgradePath（FindPath 返回多边逐级路径）
              │  path = [1.34→1.35, 1.35→1.36, 1.36→1.37]，逐跳执行
              ▼
   ┌─────────────────────────────────────────────────────┐
   │ Hop 1: 1.34 → 1.35   （PreCheck → DAG → PostCheck）  │
   │ Hop 2: 1.35 → 1.36   （PreCheck → DAG → PostCheck）  │
   │ Hop 3: 1.36 → 1.37   （PreCheck → DAG → PostCheck）  │
   └─────────────────────────────────────────────────────┘
              │  每跳之间自动衔接，仅失败时暂停
              ▼
Status.CurrentVersion = v2.7.0
```

**与标准方案的差异**：在代码层面，方案 A 与标准逐跳（§6）**共用同一机制**——用户始终只需一次 `DesiredVersion`，`ClusterVersionReconciler` 经 `FindPath` 多边路径自动逐跳（`CompleteUpgradeHop` 推进 `currentVersion`，直到等于 `desiredVersion`）。区别仅在 `UpgradePath` 里声明的是「三条逐级边」还是「单条直连边」。

#### 7.3.2 方案 B：kubeadm 层真·单跳（跳过小版本，不推荐）

尝试一次 `kubeadm upgrade apply 1.37` 直接跨 1.35/1.36。需同时满足以下前提，且官方不承诺支持：

| 验证项 | 说明 | 结论（默认） |
|--------|------|-------------|
| kubeadm `upgrade apply` 跳过校验 | 1.34 直接 apply 1.37 是否被拒绝 | 大概率拒绝 |
| apiserver 类型注册跳级 | 1.35/1.36 的对象注册/默认值迁移缺失 | 有数据风险 |
| 3 批不兼容变更一次性清理 | DRA/Workload/StorageVersionMigration 等对象删除 | 可做，但风险面大 |
| etcd 跳级迁移 | v3.5.x → v3.7.0 直接迁移 | 未验证 |

> **结论**：方案 B 仅在「kubeadm 验证通过 + 无中间版本业务依赖 + 测试环境充分验证」的极少数场景考虑，生产不推荐。

### 7.4 方案 A 详细设计（推荐）

#### 7.4.1 UpgradePath 定义（真实 CRD 字段）

> 框架无 `strategy`/`expandHops` 字段；多跳通过声明**多条逐级边**实现，`FindPath`（BFS）自动返回多边路径。API group 为 `config.openfuyao.com/v1alpha1`。

```yaml
apiVersion: config.openfuyao.com/v1alpha1
kind: UpgradePath
metadata:
  name: k8s-1.34-to-1.37
spec:
  versions:
    - version: "v2.6.0"     # 含 K8s 1.34
    - version: "v2.6.5"     # 含 K8s 1.35
    - version: "v2.6.8"     # 含 K8s 1.36
    - version: "v2.7.0"     # 含 K8s 1.37
  paths:
    - from: "v2.6.0"
      to: "v2.6.5"
    - from: "v2.6.5"
      to: "v2.6.8"
    - from: "v2.6.8"
      to: "v2.7.0"
```

#### 7.4.2 触发与编排（真实代码路径）

```
1. 用户: 修改 ClusterVersion.Spec.DesiredVersion = v2.7.0
2. ClusterVersionReconciler.reconcileUpgrade:
   a. FindPath(current=v2.6.0, desired=v2.7.0) → [v2.6.0→v2.6.5, v2.6.5→v2.6.8, v2.6.8→v2.7.0]（BFS 多边）
   b. hopTarget := path[0].To = v2.6.5
   c. 标记 BKECluster upgrade-ready=v2.6.5
3. BKEClusterReconciler 执行单跳 DAG → CompleteUpgradeHop: currentVersion=v2.6.5, Phase=Upgrading
4. 下一次 Reconcile: FindPath(current=v2.6.5, desired=v2.7.0) → 继续 v2.6.8，再 v2.7.0
5. 逐跳自动衔接，直到 currentVersion == desiredVersion（Phase=Ready）
6. 任一 hop 失败 → FailUpgradeHop → Phase=Failed，停止后续 hop
```

#### 7.4.3 不兼容变更注入（每跳 PreCheck）

每跳复用第六节 6.4/6.5 的映射表，把对应版本的 PreCheck 作为该 hop 的前置步骤注入：

| Hop | 注入 PreCheck（对应版本不兼容变更） |
|-----|-----------------------------------|
| Hop 1 | 1.35：`--pod-infra-container-image`、cgroup v1、StorageVersionMigration v1alpha1、ipvs 弃用、PreferClose |
| Hop 2 | 1.36：flex-volume、Workload v1alpha1、SnapshotMetadataService、DRA RBAC、PreBind、指标重命名 |
| Hop 3 | 1.37：Workload v1alpha2、cAdvisor Flags、SELinuxMount、eventRecordQPS、kube-proxy mode、NodeSyncPeriod |

> 若希望「一次操作前统一预检」，可在 Hop 1 之前额外跑一个**全量 PreCheck**，把 3 跳的必须处理项一次性校验并给出报告，但不改变逐跳执行的事实。

#### 7.4.4 偏差门控

- 每跳内严格满足「先控制面后 worker、kubelet ≤ apiserver」。
- Hop 1 结束时全部节点到 1.35，Hop 2 到 1.36，Hop 3 到 1.37，逐跳收敛，避免长期停留在 kubelet 滞后 3 版本的边界状态。

### 7.5 方案对比与结论

| 维度 | 标准方案（逐跳，第六节） | 直升方案 A（框架层） | 直升方案 B（kubeadm 跳级） |
|------|------------------------|---------------------|---------------------------|
| 用户操作次数 | 3 次 | 1 次 | 1 次 |
| 内部执行 | 3 跳 | 3 跳（自动衔接） | 1 跳（跳过） |
| kubeadm 合规性 | 合规 | 合规 | 不合规/需验证 |
| 不兼容变更处理 | 逐跳分散 | 逐跳注入 | 一次性（风险大） |
| 回滚粒度 | 逐跳 | 逐跳 | 仅整次 |
| 失败影响面 | 小 | 小（自动停在失败跳） | 大 |
| 适用场景 | 生产通用 | 生产（追求少人工） | 测试/特殊（不推荐生产） |

**结论**：k8s 1.34 → 1.37 的「直升」应采用**方案 A（框架层直升）**——用户一次操作、框架内部自动 3 跳，既满足 kubeadm 逐小版本约束，又保留逐跳 PreCheck/PostCheck 与回滚点。方案 B 仅在极端测试场景评估，生产禁用。

## 八、k8s 1.34 真·直升 1.37 设计方案（kubeadm 跳级）

> 本章基于 `cluster-api-provider-bke` 仓库**实际代码**校准。核心结论：框架的升级路径引擎（`UpgradePath` + `FindPath` + `ClusterVersionReconciler` + 声明式 DAG）对「跳级」**没有任何门禁**——真·直升天然可表达为 `UpgradePath` 中的**一条直连边**，一次 DAG 完成。真正的工程缺口是「跳级安全门禁」缺失，本方案的重点即落在补门禁与前置校验上。

### 8.1 代码事实（真直升如何在现有框架中落地）

| 机制 | 代码位置 | 关键行为 |
|------|---------|---------|
| 路径查找 | `pkg/upgradepath/graph.go:144` `FindPath` | BFS 最短路径，跳过 `blocked` 边；单条直连边 `1.34→1.37` 直接返回单边路径 |
| 单跳触发 | `controllers/clusterversion/clusterversion_controller.go:177` | `hopTarget := path[0].To`，打 `cvo.openfuyao.cn/upgrade-ready` 注解 |
| DAG 执行 | `controllers/capbke/bkecluster_upgrade_dag.go:53` `executeUpgradeDAG` | 读 `upgrade-ready` → 解析 ReleaseImage bundle → 构建 DAG → `Scheduler.ExecuteDAG` |
| 版本判定 | `pkg/upgrade/context.go:121` `NeedsUpgrade` | 纯字符串 `current != target`，**无 minor-diff 校验** |
| 语义比较 | `pkg/phaseframe/phaseutil/util.go:1146` `NeedUpgrade` | hashicorp go-version，仅判断 `new > old`，**不校验跳级** |
| 版本注入 | `pkg/upgrade/spec_sync.go:26` | `ApplyVersionContextTargetsToClusterSpec` 把 etcd/containerd/kubernetes target 写入 `BkeConfig.Cluster` |
| 组件映射 | `pkg/upgrade/catalog.go:54` | `kubernetes-master`→`EnsureMasterUpgrade`、`etcd`→`EnsureEtcdUpgrade`、`kubernetes-worker`→`EnsureWorkerUpgrade` |

> **推论**：不需要新增 CRD 字段或编排器。真·直升 = 在 `UpgradePath.spec.paths` 声明 `{from: "v2.6.0", to: "v2.7.0"}` 直连边；`FindPath` 返回单边，框架单跳执行。`VersionContext` 里 `kubernetes-master` 的 current=1.34 / target=1.37，`EnsureMasterUpgrade` 即向节点下发一次跳级的 kubeadm 升级命令。

### 8.2 直连边声明（真实 UpgradePath CRD）

API group 为 `config.openfuyao.com/v1alpha1`，字段只有 `from/to/blocked/deprecated/notes/preCheck/postCheck`（无 `strategy`/`expandHops`/`handler`）：

```yaml
apiVersion: config.openfuyao.com/v1alpha1
kind: UpgradePath
metadata:
  name: k8s-1.34-to-1.37-direct
spec:
  versions:
    - version: "v2.6.0"      # 含 K8s 1.34
      installable: true
    - version: "v2.7.0"      # 含 K8s 1.37
      installable: true
  paths:
    - from: "v2.6.0"
      to: "v2.7.0"           # 直连边：跳过 1.35/1.36
      blocked: false
      deprecated: false
      notes: "kubeadm skip-minor upgrade; requires gate in 8.5"
      preCheck:
        - name: kubeadm-skip-minor-supported
          required: true
        - name: etcd-direct-migration-verified
          required: true
        - name: apiserver-storage-version-compatible
          required: true
      postCheck:
        - name: control-plane-version
          required: true
        - name: kubelet-version
          required: true
```

### 8.3 单跳 reconcile 流程（真实代码路径）

```
1. 用户: ClusterVersion.Spec.DesiredVersion = v2.7.0
2. ClusterVersionReconciler.reconcileUpgrade (clusterversion_controller.go):
   a. FindPath(current=v2.6.0, desired=v2.7.0) → [ {from:v2.6.0, to:v2.7.0} ]   ← 单边
   b. hopTarget := path[0].To  = v2.7.0
   c. ensurer.Ensure(ReleaseImage v2.7.0 拉取并 Valid)
   d. markUpgradeReady: BKECluster 注解 upgrade-ready=v2.7.0, upgrade-path="v2.6.0->v2.7.0"
3. BKEClusterReconciler.executeUpgradeDAG (bkecluster_upgrade_dag.go):
   a. declarativeUpgradeTargetVersion = v2.7.0
   b. resolveUpgradeBundle(v2.7.0) → bundle（kubernetes-master/etcd 等组件为 1.37/v3.7.0）
   c. BuildAndSetVersionContextFromBundle(bundle, currentBundle)
        currentBundle 来自 v2.6.0 的 ReleaseImage（kubernetes-master=1.34, etcd=v3.5.x）
   d. SyncUpgradeTargetsToClusterSpec → Spec.ClusterConfig.Cluster.{KubernetesVersion=1.37,EtcdVersion=v3.7.0}
   e. BuildDAGFromBundle → Scheduler.ExecuteDAG（单次）
   f. completeDeclarativeUpgrade → CompleteUpgradeHop：currentVersion=v2.7.0, Phase=Ready
```

> 与逐跳方案的**唯一区别**是 `paths` 里只声明了一条直连边；`FindPath` 少返回中间边，`executeUpgradeDAG` 少执行两次。其余代码路径完全复用。

### 8.4 单跳 DAG 与版本流

`VersionContext`（current 来自 v2.6.0 bundle，target 来自 v2.7.0 bundle）：

| 组件 | current | target | 决策 |
|------|---------|--------|------|
| kubernetes-master | v1.34.0 | v1.37.0 | Upgrade（跳级） |
| kubernetes-worker | v1.34.0 | v1.37.0 | Upgrade（跳级） |
| etcd | v3.5.x | v3.7.0 | Upgrade（跳级） |
| containerd / kube-proxy / coredns | … | … | 按需 Upgrade |

DAG 依赖来自 bundle 内 `ComponentVersion.spec.dependencies`（非硬编码），典型顺序：

```
pre-upgrade-resources → etcd → kubernetes-master → kubernetes-worker → {kube-proxy, coredns}
```

版本注入点：`ApplyVersionContextTargetsToClusterSpec`（`pkg/upgrade/spec_sync.go`）把 target 写入 `BkeConfig.Cluster.KubernetesVersion`，BKEAgent 侧的 `EnsureMasterUpgrade` 据此下发 `kubeadm upgrade`（`pkg/job/builtin/kubeadm/command.go`），kubeadm 收到的即「1.34 → 1.37」跳级目标。

### 8.5 代码缺口与落地改造（优化重点）

**缺口 1：框架无跳级门禁。** `FindPath` 只做 BFS，`NeedsUpgrade`/`NeedUpgrade` 均不校验 minor 差。若不补门禁，误声明一条直连边即可触发跳级升级。改造两点（选一或组合）：

```go
// ① 控制器层门禁：clusterversion_controller.go 的 reconcileUpgrade 内，markUpgradeReady 之前
// 校验 current 与 hopTarget 的 minor 差，跨 >1 个小版本时要求显式 allow。
func validateSkipMinor(current, hopTarget string, allow bool) error {
    c, _ := semver.ParseTolerant(current)
    t, _ := semver.ParseTolerant(hopTarget)
    if t.Minor-c.Minor > 1 && !allow {
        return fmt.Errorf("refusing skip-minor upgrade %s -> %s (missing allow)", current, hopTarget)
    }
    return nil
}

// ② 路径层门禁：直连边的 preCheck 必须包含 required 检查项（见 8.2 的 CheckStep），
// 由 UpgradePath 校验/执行器消费，缺失时该边视为 blocked。
```

**缺口 2：`preCheck/postCheck` 目前仅做结构校验（`ValidateRules` 检查 name 非空），无执行器。** 真直升必须把三版本合并的校验项落到 `CheckStep` 并接入执行，否则 8.2 的 `preCheck` 是空声明。

### 8.6 一次性合并 PreCheck（三版本合并为边上的 required 检查项）

把 1.35+1.36+1.37 三批必须处理项（详见第六节 6.5）合并为直连边 `preCheck` 的 required 检查项，在 DAG 的 `pre-upgrade-resources` 阶段统一执行：

| CheckStep.Name | 覆盖内容 |
|----------------|---------|
| kubelet-flags-cleanup | 1.35 `--pod-infra-container-image`；1.37 cAdvisor 系列（仅留 `--housekeeping-interval`） |
| removed-api-objects-cleanup | 1.35 StorageVersionMigration v1alpha1；1.36 Workload v1alpha1 / SnapshotMetadataService；1.37 Workload v1alpha2 / PodCertificateRequest 字段 |
| environment-gate | 1.35 cgroup v1；1.36 flex-volume / DRA RBAC / PreBind / 指标；1.37 SELinuxMount / eventRecordQPS / kube-proxy mode / NodeSyncPeriod |
| kubeadm-skip-minor-supported | 验证 kubeadm `upgrade plan v1.37.0` 放行跳级 |
| etcd-direct-migration-verified | v3.5.x → v3.7.0 直接迁移演练通过 |
| apiserver-storage-version-compatible | 1.35/1.36 类型注册/默认值/字段删除已评估 |

> **核心风险**：逐跳方案中，中间版本（如 1.35）在「对象删除后」继续运行一段窗口，可渐进暴露隐藏依赖；真直升把三批校验压到一次执行，**没有渐进暴露机会**，遗漏项会一次性在 1.37 暴露。

### 8.7 控制面与 worker 升级

控制面由 `EnsureMasterUpgrade` 在节点执行 kubeadm（版本取自 `BkeConfig.Cluster.KubernetesVersion=1.37`）；HA 其余 master 走 `kubeadm upgrade node`。worker 由 `EnsureWorkerUpgrade` 逐节点 drain 后升 kubelet：

```bash
# 控制面（首个 master）—— agent 侧等价命令
kubeadm upgrade plan v1.37.0
kubeadm upgrade apply v1.37.0

# worker 逐节点（框架 EnsureWorkerUpgrade 内 drain/uncordon）
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
kubeadm upgrade node
kubectl uncordon <node>
```

- kubelet 1.34 → 1.37 偏差差 3（阈值内）；升级窗口内必须控制面先到 1.37，worker 后升。
- etcd 跳 `v3.7.0` 是最高风险环节，必须在 8.6 `etcd-direct-migration-verified` 演练通过后执行。

### 8.8 风险与回滚

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| apiserver 存储版本迁移缺失（跳 1.35/1.36 类型注册） | 数据不一致/对象损坏 | 8.6 逐项门禁 + 测试环境全量演练 + etcd 快照 |
| etcd v3.5.x → v3.7.0 跳级迁移失败 | 集群失联 | 升级前快照；手动 etcdctl 恢复预案 |
| kubeadm 拒绝跳级 | 无法 apply | 门禁 `kubeadm-skip-minor-supported` 提前验证；失败退回逐跳 |
| 回滚无 n-1 中间态 | 只能整次回 1.34 | etcd 快照恢复 + 全量回 1.34 |

回滚路径（仅整次回 1.34）：`etcd 快照恢复 → 控制面镜像回 1.34 → worker kubelet 回 1.34 → 依赖组件回退`。升级窗口期写入数据在回滚时丢失，需提前冻结写入。

### 8.9 结论

真·直升在现有框架中**无需新增 CRD/编排器**，仅需在 `UpgradePath` 声明一条直连边即可单跳执行；但框架**缺少跳级门禁**，落地必须补两处：① `reconcileUpgrade` 内 `validateSkipMinor` minor-diff 校验；② 直连边 `preCheck` 的 required 检查项（含 kubeadm/etcd/apiserver 跳级验证）接入执行器。仅当这两处门禁 + 8.6 三批合并 PreCheck 全部通过、且业务容忍一次性重建、具备 etcd 快照回滚能力时，才允许进入真·直升；否则回退标准逐跳（§6）。

> **与 §7 的关系修正**：§7 中「方案 A（框架层直升）需 `strategy/expandHops` 字段」的表述与实际代码不符——实际框架通过 `FindPath` 对**多条边自动逐跳**实现多跳升级（标准方案 §6 即如此，用户始终只需一次 `DesiredVersion`）。因此「真·直升」与「逐跳」在代码层的真正区别，仅在于 `paths` 声明的是**单条直连边**还是**三条逐级边**。

## 九、preCheck/postCheck 执行器设计

> §8.5 指出框架缺口：`UpgradePathRule.PreCheck/PostCheck` 目前仅有结构体字段、无执行器。本章给出执行器设计，复用已有 KEP-5-2（`code/kep/kep5/kep5-2-precheck-postcheck-design-v2.md`）的 `CheckItem`/`CheckRegistry`/`CheckRunner`/`CheckReport` 定义，聚焦「如何接入真实声明式升级流程」。

### 9.1 现状与缺口

| 项 | 现状 | 缺口 |
|----|------|------|
| 数据模型 | `api/v1alpha1/upgradepath_types.go`：`UpgradePathRule.PreCheck/PostCheck []CheckStep`，`CheckStep{Name, Required}` | 仅存 name+required，无 timeout/params/deps |
| 校验 | `pkg/upgradepath/graph.go:295 ValidateRules`：仅校验 `CheckStep.Name` 非空 | 不校验 name 是否可执行 |
| 执行 | 无 | `ClusterVersionReconciler` 只把 `Phase` 置为 `PreChecking`（`clusterversion_controller.go:201`），**未真正执行任何检查** |
| 结果 | 无 | 检查结果未持久化、不可观测 |

> **结论**：`preCheck/postCheck` 当前是「纯声明」；需引入执行器把 `CheckStep.Name` 映射到真正可执行的检查项，并在升级前/后落地门禁。

### 9.2 执行器架构（复用 KEP-5-2）

```
UpgradePathRule.preCheck/postCheck  (name + required, 引用式声明)
        │
        ▼  CheckPolicyResolver（把 name 解析为完整 CheckStep，含 timeout/params/deps）
CheckPolicy CRD (cvo/v1beta1)  →  完整 CheckStep{Name, Required, Timeout, Params, Dependencies, RetryCount, Condition}
        │
        ▼  CheckRegistry（name → CheckItem 实现）
CheckRunner（DAG 拓扑执行 + 超时 + 重试 + required 门禁）
        │
        ▼  CheckReport → 写成 ClusterVersion.Status.PreCheckReport / PostCheckReport
```

职责分离（与 KEP-5-2 一致）：
- **UpgradePath** 只声明「要检查什么」（`name` + `required`），随 OCI 镜像发布。
- **CheckPolicy CRD** 定义「怎么检查」（timeout/params/deps），由集群运维在 K8s 侧维护，可环境定制。
- **CheckItem（执行器）** 是 Go 实现，通过 `CheckRegistry.Register` 插件式接入。

### 9.3 核心接口与执行器

```go
// pkg/check/item.go —— CheckItem 执行器接口（KEP-5-2 §5.3）
type CheckItem interface {
    Name() string
    Execute(ctx context.Context, cluster *bkev1beta1.BKECluster, params map[string]string) (*CheckResult, error)
    Phase() CheckPhase // pre / post / both
}

// pkg/check/registry.go —— 注册表（KEP-5-2 §6.1）
type CheckRegistry struct { mu sync.RWMutex; registry map[string]CheckItem }
func (r *CheckRegistry) Register(item CheckItem)
func (r *CheckRegistry) Get(name string) (CheckItem, bool)

// pkg/check/runner.go —— 执行器（KEP-5-2 §6.3，简化签名）
type CheckRunner struct { registry *CheckRegistry; resolver *CheckPolicyResolver }
func (r *CheckRunner) RunPreChecks(ctx context.Context, cluster *bkev1beta1.BKECluster, refs []v1alpha1.CheckStep) (*CheckReport, error)
func (r *CheckRunner) RunPostChecks(ctx context.Context, cluster *bkev1beta1.BKECluster, refs []v1alpha1.CheckStep) (*CheckReport, error)
```

`CheckResult`/`CheckReport`/`CheckStatus`（Passed/Failed/Skipped/Timeout）定义见 KEP-5-2 §5.2；`CheckRunner` 内部含 DAG 拓扑排序 + 事件驱动图执行 + 超时/重试 + required 失败即中止（KEP-5-2 §6.3，此处不重复）。

### 9.4 接入真实代码流程

**PreCheck 接入点**（`controllers/clusterversion/clusterversion_controller.go` `reconcileUpgrade`）：

```go
// 现逻辑（201-209）：置 Phase=PreChecking → markUpgradeReady
// 改造后：在 markUpgradeReady 之前执行 preCheck
report, err := r.checkRunner.RunPreChecks(ctx, bc, path[0].PreCheck)
if err != nil || reportHasRequiredFailure(report) {
    r.setStatus(ctx, cv, statusPatch{ Phase: phasePtr(PreCheckFailed),
        Conditions: conditionPtr(failureCondition("PreCheckFailed", reportSummary(report))) })
    return ctrl.Result{}, nil   // 不标记 upgrade-ready，阻断升级
}
r.setStatus(ctx, cv, statusPatch{ Phase: phasePtr(PreChecking), ... })
r.markUpgradeReady(...)
```

**PostCheck 接入点**（`controllers/capbke/bkecluster_upgrade_dag.go` `completeDeclarativeUpgrade`，`CompleteUpgradeHop` 之前）：

```go
report, err := r.checkRunner.RunPostChecks(ctx, bkeCluster, path.PostCheck)
if err != nil || reportHasRequiredFailure(report) {
    // 不推进 currentVersion，保持 ClusterUpgrading，进入重试/告警
    return fmt.Errorf("post-check failed: %s", reportSummary(report))
}
return clusterversion.CompleteUpgradeHop(ctx, r.Client, cv, hopTarget)
```

**执行时序**：

```
PreCheck（ClusterversionReconciler）              DAG（BKEClusterReconciler）               PostCheck
─────────────────────────────────▼──────────────────────────────────────────────▼──────────
FindPath → 解析 ReleaseImage → RunPreChecks → markUpgradeReady → executeUpgradeDAG → RunPostChecks → CompleteUpgradeHop
```

### 9.5 检查项清单与注册（1.34 → 1.37）

**通用检查项**（KEP-5-2 已定义，直接复用）：`cluster-health`、`backup-verification`、`resource-check`、`component-dependency`（pre）；`component-version`、`cluster-health`、`node-ready`、`application-health`（post）。

**1.34 → 1.37 特有检查项（落在 UpgradePathRule.preCheck，见 §8.6）**：

| CheckItem.Name | Phase | 检查内容 | 真直升是否 required |
|----------------|-------|---------|--------------------|
| `kubelet-flags-cleanup` | pre | `--pod-infra-container-image`、cAdvisor 系列 Flags 已清理 | 是 |
| `removed-api-objects-cleanup` | pre | StorageVersionMigration v1alpha1、Workload v1alpha1/v1alpha2、SnapshotMetadataService 等对象已删除 | 是 |
| `environment-gate` | pre | cgroup v2 / flex-volume / SELinuxMount / eventRecordQPS / kube-proxy mode | 是 |
| `kubeadm-skip-minor-supported` | pre | `kubeadm upgrade plan v1.37.0` 放行跳级 | 是 |
| `etcd-direct-migration-verified` | pre | v3.5.x → v3.7.0 直接迁移通过（快照演练） | 是 |
| `apiserver-storage-version-compatible` | pre | 1.35/1.36 类型注册/默认值/字段删除已评估 | 是 |

**注册示意**：

```go

    // ...
}
```

### 9.6 执行语义与门禁

- **required=true**：失败/超时 → 整体 `CheckReport.Status=Failed`，PreCheck 阻断（`Phase=PreCheckFailed`）、PostCheck 阻断（不推进 `currentVersion`）。
- **required=false**：失败仅记录告警，不阻断。
- **逐个超时 + 重试 + 依赖**：由完整 `CheckStep`（来自 CheckPolicy）提供 `Timeout`/`RetryCount`/`Dependencies`，`CheckRunner` 内 DAG 拓扑执行（KEP-5-2 §6.3）。
- **真直升（§8）专属**：直连边 `preCheck` 全 required，任一项失败即停，回退标准逐跳（§6）。

### 9.7 报告与可观测性

- `CheckReport` 写入 `ClusterVersion.Status.PreCheckReport` / `PostCheckReport`（字段见 KEP-5-2 §5.2）。
- 事件：`PreCheckFailed` / `PreCheckPassed` / `PostCheckFailed`（`Recorder.Event`）。
- 指标：`bke_precheck_duration_seconds`、`bke_precheck_failed_total`（按 `name` 分标签）。
