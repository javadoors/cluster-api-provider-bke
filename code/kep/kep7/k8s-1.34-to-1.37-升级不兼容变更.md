## Summary

本 KEP 设计 Kubernetes v1.34 → v1.37 的升级方案。1.34 → 1.37 跨越 3 个小版本，期间**没有内置资源组版本的批量移除**（官方「按版本移除的 API」最新只到 v1.32 flowcontrol v1beta3），变更集中在 feature-gate 收紧、Flags/字段移除、指标重命名、默认行为改变，以及 alpha/beta API 迁移（DRA、Workload/PodGroup、StorageVersionMigration、PodCertificate 等）。

本 KEP 覆盖四部分：

1. **不兼容变更清单**：按版本（v1.34/1.35/1.36/1.37）梳理组件启动失败类、API 对象移除类、第三方集成改造类、指标重命名类、默认行为改变类。
2. **升级路径方案**：标准逐跳（3 hop）、框架层直升（单次操作 + 内部自动多跳）、真·直升（kubeadm 跳级）三种策略与选型。
3. **执行器设计**：preCheck/postCheck 执行器（复用 KEP-5-2 的 `CheckItem`/`CheckRegistry`/`CheckRunner`）。
4. **组件版本配套**：k8s v1.37 配套组件版本矩阵、差异分析、逐组件升级详细设计，以及核心组件 YAML 模板 v1.37 合规性检查与修复。

## Motivation

- **跨 3 个小版本**：1.34 → 1.37 控制面不允许跳级，需逐小版本升级（3 hop）或评估跳级方案，停机窗口与风险显著高于单版本升级。
- **不兼容变更累积**：1.35/1.36/1.37 三批不兼容变更需在对应版本处理，遗漏会导致组件启动失败或资源静默失效。
- **声明式框架支持**：openFuyao/CAPBKE 已有声明式升级框架（`UpgradePath + FindPath + ClusterVersionReconciler + DAG`），但缺少跳级门禁与检查执行器。

### Goals

- 建立 1.34 → 1.37 完整的不兼容变更清单，作为升级前 PreCheck 的依据。
- 给出安全的升级路径（逐跳 + 直升）与选型建议。
- 设计 preCheck/postCheck 执行器，将升级前/后校验从「人工确认」落地为「可执行、可观测的门禁」。
- 明确 k8s v1.37 组件版本配套与 YAML 合规性修复项。

### Non-Goals

- 不涉及业务应用的 API 适配与镜像重构建。
- 不定义 UI/CLI 层的检查结果展示。
- 不替换现有兼容性校验逻辑（`CheckCompatibility`），仅作补充。
- 不定义特定第三方（calico/coredns/containerd）确切 patch 版本（需按上游 release notes 逐项确认）。

### 升级路径方案概览

| 方案 | 用户操作 | 内部执行 | kubeadm 合规性 | 适用 | 结论 |
|------|---------|---------|---------------|------|------|
| **标准逐跳**（§6） | 1 次 `DesiredVersion` | 3 跳自动衔接 | 合规 | 生产通用 | ✅ 推荐 |
| **框架层直升**（§7 方案A） | 1 次 | 3 跳（框架内部） | 合规 | 生产（少人工） | ✅ 与标准逐跳同机制 |
| **真·直升**（§8 方案B） | 1 次 | 1 跳（kubeadm 跳级） | 不合规/需门禁 | 测试/特殊 | ⚠️ 需批准 + 演练 |

> **关键发现**：框架 `FindPath`（BFS）对「跳级」无门禁——标准逐跳与框架层直升在代码层**共用同一机制**（声明多条逐级边，`ClusterVersionReconciler` 自动逐跳）；「真·直升」仅需声明单条直连边即可单跳执行。真正需要补的是**跳级安全门禁**（`validateSkipMinor`）与**检查执行器**。

## Design Details

### 升级路径与策略

#### 标准逐跳方案（3 hop）

```
1.34 ──▶ 1.35 ──▶ 1.36 ──▶ 1.37
  Hop 1      Hop 2      Hop 3
```

- **路径引擎**：`UpgradePath` 声明三条逐级边，`FindPath`（`pkg/upgradepath/graph.go:144`，BFS）返回多边路径；`ClusterVersionReconciler` 取 `path[0].To` 打 `upgrade-ready` 注解，`BKEClusterReconciler.executeUpgradeDAG` 单跳执行，`CompleteUpgradeHop` 推进 `currentVersion` 自动进入下一跳。
- **单跳标准流程**：① 升级前预检（etcd 快照、健康检查、清理被移除 API 对象/Flags）→ ② 升级控制面（`kubeadm upgrade apply/node`）→ ③ 升级 kubelet/kube-proxy（master）→ ④ 升级 worker（逐节点 drain/uncordon）→ ⑤ 升级后验证。
- **逐跳不兼容变更映射**：Hop 1 处理 1.35 变更（`--pod-infra-container-image`、cgroup v1、StorageVersionMigration v1alpha1、ipvs 弃用）；Hop 2 处理 1.36 变更（flex-volume、Workload v1alpha1、SnapshotMetadataService、DRA RBAC、PreBind、指标重命名）；Hop 3 处理 1.37 变更（Workload v1alpha2、cAdvisor Flags、SELinuxMount、eventRecordQPS、kube-proxy mode）。

#### 框架层直升方案（单次操作 + 内部自动 3 跳）

与标准逐跳共用同一机制——用户只需一次 `DesiredVersion`，`ClusterVersionReconciler` 经 `FindPath` 多边路径自动逐跳。区别仅在 `UpgradePath` 声明的是「三条逐级边」还是「单条直连边」。详见 [Alternatives](#alternatives)。

#### 真·直升方案（kubeadm 跳级，实验性）

- **本质**：`UpgradePath` 声明单条直连边 `{from: v2.6.0, to: v2.7.0}`，`FindPath` 返回单边，框架单跳执行，`VersionContext` current=1.34 → target=1.37。
- **代码缺口**：`FindPath` 无 minor-diff 校验、`NeedsUpgrade` 纯字符串比较，框架不会阻止跳级。落地须补两处：
  1. `reconcileUpgrade` 内 `validateSkipMinor` minor-diff 校验；
  2. 直连边 `preCheck` 的 required 检查项（`kubeadm-skip-minor-supported`、`etcd-direct-migration-verified`、`apiserver-storage-version-compatible`）接入执行器。
- **风险**：丧失 apiserver 存储版本迁移与中间版本渐进回滚能力；生产默认禁用，仅在极小规模 + 完整 etcd 回滚能力 + 测试演练通过时评估。

### preCheck/postCheck 执行器设计

复用 KEP-5-2（`code/kep/kep5/kep5-2-precheck-postcheck-design-v2.md`）的 `CheckItem`/`CheckRegistry`/`CheckRunner`/`CheckReport` 定义。

```
UpgradePathRule.preCheck/postCheck（name + required，引用式声明）
  │  CheckPolicyResolver（解析为完整 CheckStep，含 timeout/params/deps）
  ▼
CheckPolicy CRD → 完整 CheckStep
  │  CheckRegistry（name → CheckItem 实现）
  ▼
CheckRunner（DAG 拓扑执行 + 超时 + 重试 + required 门禁）
  │
  ▼
CheckReport → ClusterVersion.Status.PreCheckReport / PostCheckReport
```

- **接入点**：
  - PreCheck：`ClusterVersionReconciler.reconcileUpgrade` 中 `Phase=PreChecking` 之后、`markUpgradeReady` 之前调用 `RunPreChecks`，失败 → `Phase=PreCheckFailed`，不标记 `upgrade-ready`。
  - PostCheck：`BKEClusterReconciler.completeDeclarativeUpgrade` 中 `CompleteUpgradeHop` 之前调用 `RunPostChecks`，required 失败 → 不推进 `currentVersion`。
- **检查项清单**：通用（`cluster-health`/`backup-verification`/`component-version`/`node-ready` 等）+ 1.34→1.37 特有（`kubelet-flags-cleanup`/`removed-api-objects-cleanup`/`environment-gate`/`kubeadm-skip-minor-supported`/`etcd-direct-migration-verified` 等）。

### 核心组件 YAML 模板合规性修复

仓库核心组件 YAML 模板（`utils/bkeagent/mfutil/tmpl/k8s/*`、`pkg/job/builtin/kubeadm/kubelet/tmpl/*`）对 v1.37 的合规性检查与修复：

1. **阻断级**：`kubelet.service.tmpl:13` 无条件输出 `--pod-infra-container-image`（1.35 已移除）→ 删除该行 + `run.go` 移除 `podInfraContainerImage` 赋值。
2. **版本不满足**：`versions.yaml` etcd `v3.6.7`→`v3.7.0-of.1`、k8s `v1.34.3`→`v1.37.0-of.1`、pause `3.9`→`3.10`；`validation.go` `MaxSupportedK8sVersion` `v1.28.0`→`v1.37.0`。
3. **条件风险**：scheduler GPU `--use-legacy-policy-config`（1.24 移除）按 `vlt v1.24.0` 门控；kube-proxy `mode` 显式化（弃用 ipvs）。
4. **通过项**：cAdvisor 弃用 Flags、`--cloud-config`/`--register-schedulable`、`DeclarativeValidationTakeover` 均未在模板出现，无需处理。

### 组件版本差异与逐组件升级设计

DAG 拓扑（依据 `component.yaml` 的 `dependencies`）：

```
pre-upgrade-resources ─┬─ provider ─► bkeagent ─► containerd ─► etcd
                       │                                            │
                       └────────────────────────────────────────────┼──► kubernetes-master ─┬─► calico
                                                                     ├──► kubernetes-worker  ├─► kubeproxy
                                                                     (偏差门控保证先后)        └─► coredns
```

逐组件升级（执行器/机制基于仓库现有 handler）：

| 组件 | 执行器 | 关键要点 |
|------|--------|---------|
| kubernetes-master | `EnsureMasterUpgrade`（inline） | `Kubeadm UpgradeControlPlane` 逐 master；目标版本经 `spec_sync.go` 写 `BkeConfig.Cluster.KubernetesVersion` |
| kubernetes-worker | `EnsureWorkerUpgrade`（inline） | drain → `Kubeadm UpgradeWorker` → uncordon，非阻塞 |
| kubeproxy | manifest（SSA） | DaemonSet 滚动；`mode` 显式化 |
| etcd | `EnsureEtcdUpgrade`（inline） | 快照后逐节点 `Kubeadm UpgradeEtcd`；`etcdVersionsMatch` 比对 |
| containerd | `EnsureContainerdUpgrade`（inline） | `reset` + `redeploy`；pause 随 `pinned_images.sandbox` 更新 |
| calico / coredns | manifest（SSA） | 滚动；calico 先查兼容矩阵 |

**etcd 数据兼容性**：v3.6.7 → v3.7.0 属相邻 minor 升级，3.x 内数据格式兼容、滚动期成员可混合（差 ≤1 minor）；降级仅限 n-1；需核对 StorageVersion 跳变与 `-of.X` 补丁影响。

**containerd 配置兼容性**：仓库配置已对齐 containerd 2.x（`config.toml` `version = 3`、`pinned_images.sandbox` 新键位），同大版本内升级基本兼容；需核对 minor 是否变更 config version/插件字段。

## Graduation Criteria

- **Alpha**：不兼容变更清单评审通过；`validateSkipMinor` + `CheckRunner` 落地；组件 YAML 模板修复完成。
- **Beta**：标准逐跳方案在测试集群 1.34→1.37 全流程跑通；preCheck/postCheck 门禁阻断/通过场景验证通过。
- **GA**：生产灰度升级完成；回滚预案（etcd 快照 + 全量回 1.34）演练通过；监控告警与指标重命名同步完成。

## Drawbacks

- **跳级风险**：真·直升丧失 apiserver 存储版本迁移与中间版本渐进回滚能力。
- **不兼容变更一次性暴露**：直升方案把 3 批 PreCheck 压到一次执行，无渐进暴露机会，遗漏项会一次性爆发。
- **第三方后缀不确定性**：`-of.X` 为 openFuyao 自建补丁，组件数据/配置兼容性需以 openFuyao 发布为准。

## Alternatives

1. **标准逐跳 vs 框架层直升**：二者在代码层共用 `FindPath` 多边路径机制，用户侧均为单次 `DesiredVersion`；区别仅为声明边数。逐跳提供中间版本渐进验证，为生产首选。
2. **真·直升 vs 逐跳**：真·直升仅在极小规模 + 极短停机窗口 + 完整回滚能力时评估；逐跳为默认。
3. **CheckPolicy 独立 CRD vs 内联 CheckStep**：采用 KEP-5-2 的 `CheckPolicy` 独立 CRD，实现检查策略与升级路径职责分离（`UpgradePath` 只声明 name+required，CheckPolicy 定义 timeout/params/deps）。

## Risks and Mitigations

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| kubeadm 拒绝跳级（真·直升） | 无法 apply | 门禁 `kubeadm-skip-minor-supported` 提前验证；失败退回逐跳 |
| apiserver 存储版本迁移缺失 | 数据不一致/对象损坏 | 逐跳方案 + 测试演练 + etcd 快照 |
| etcd v3.6→v3.7 迁移失败 | 集群失联 | 升级前快照；手动 `etcdctl` 恢复预案 |
| 不兼容变更遗漏 | 组件启动失败/资源失效 | preCheck 门禁（required 项）+ 全量 PreCheck 报告 |
| kubelet `--pod-infra-container-image` 残留 | kubelet 启动失败 | §10 模板修复（删除该 flag） |
| 回滚无 n-1 中间态（真·直升） | 只能整次回滚 | 仅整次回 1.34 + 冻结写入 |

## Infrastructure Needed

- **镜像制品**：目标版本组件镜像（k8s 1.37、etcd 3.7.0、pause 3.10、calico/containerd/coredns 配套版本）上传至制品仓库。
- **ReleaseImage**：新增 `v2X.XX` ReleaseImage（`release.yaml` + `components/*/component.yaml`），声明 1.37 组件清单与 inline 处理。

## Appendix A：不兼容变更明细

### A.1 v1.34（从 1.33 升级）

**必须处理（会直接导致失败/行为改变）**：
- kubelet 移除 `--cloud-config`、`--register-schedulable` 标志（配置即启动失败）。
- 移除 `LegacySidecarContainers`、`DevicePluginCDIDevices`、`PodDisruptionConditions` 等已 GA 的 feature gate。
- DRA API 迁移/清理：删除 kubelet gRPC `v1alpha4`；`resource.k8s.io/v1alpha3` 仅保留 `DeviceTaintRule`，其余类型移除（升级前删除 `<1.32` 存储的 resourceclaims/resourceclaimtemplates/deviceclasses/resourceslices）；`admin-access` 标签由 `resource.k8s.io/admin-access` 改为 `resource.kubernetes.io/admin-access`。
- 移除 gogo/protobuf（`cri-api`、`deviceplugin`、`podresources`、`kms/apis`、`externaljwt`、`pluginregistration` 等包）。
- 移除 REST 客户端 streaming（typed/dynamic/metadata client 的 `List()` streaming 与 `kubernetes.io/initial-events-list-blueprint` 注解）。

### A.2 v1.35（从 1.34 升级）

**必须处理**：
- kubelet 移除 `--pod-infra-container-image`（非 kubeadm 需删配置；kubeadm 需删 `extraArgs`）。
- cgroup v1 弃用（`failCgroupV1` 默认 true）：kubelet ≥1.35 在 cgroup v1 主机默认无法启动；kubeadm preflight SystemVerification 报错，可 `failCgroupV1:false` 或忽略 preflight 规避。
- kube-proxy `ipvs` 模式弃用，建议迁移 nftables/iptables。
- `StorageVersionMigration` 移除 `v1alpha1`（仅留 `v1beta1`）：升级前删除所有 v1alpha1 对象。
- 移除 `StrictCostEnforcementForVAP`、`StrictCostEnforcementForWebhooks` feature gate。
- Go API 类型移除 gogo/protobuf（构建标签 `kubernetes_protomessage_one_more_release` 可暂缓一版，1.36 彻底移除）。
- Pod resize 仅允许 CPU/内存；`Partitionable Devices`（alpha）向后不兼容；`trafficDistribution=PreferClose` 弃用（改 `PreferSameZone`）。

### A.3 v1.36（从 1.35 升级）

**必须处理（ACTION REQUIRED）**：

### A.4 v1.37（从 1.36 升级）

**必须处理（ACTION REQUIRED）**：
- `SELinuxMount` GA（默认开启）：对启用 SELinux 的集群可能破坏工作负载；升级前按官方博客排查/修复或选择退出。
