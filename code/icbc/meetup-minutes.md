## 一、openFuyao 平台整体规划介绍

openFuyao 社区向工行团队介绍了平台的整体架构与演进规划，重点阐述了两大核心建设主线：

### 1.1 声明式升级框架

openFuyao 正在构建企业级声明式升级框架，实现集群全生命周期的自动化管理。该框架基于 DAG（有向无环图）编排引擎，支持组件依赖管理和并行执行优化能力。

**核心特性**：
- **声明式 API**：通过 `ComponentVersion` CRD 声明组件版本与依赖关系
- **多类型组件支持**：统一支持 binary（二进制）、helm（Chart）、yaml（清单）、inline（内联）四种组件类型
- **三层状态机**：集群级、节点级、组件级分层状态管理，精确控制升级流程
- **可观测性**：升级进度实时展示、状态查询、事件日志、指标监控四大能力

### 1.2 核心组件 Operator 化

openFuyao 规划将核心组件改造为 Operator 模式，实现声明式版本管理。

**规划范围**：
- **版本管理 Operator（CVO）**：管理集群版本生命周期，协调所有 Operator 升级
- **基础设施 Operator**：网络（CNO）、存储（CSO）、DNS、Ingress 等
- **K8s 核心组件 Operator**：API Server、Controller Manager、Scheduler、etcd
- **扩展 Operator**：监控、认证、备份等

## 五、技术议题讨论

### 5.1 升级兼容性工具

**背景**：跨版本升级时，需识别 API 变更、配置变更、依赖变更等兼容性问题。

**讨论结论**：

升级兼容性检查应采用"**自动扫描 + 人工核对**"的双层机制：

1. **自动扫描层**：
   - 开发兼容性扫描工具，基于版本差异自动识别不兼容点
   - 扫描范围：API 版本变更、CRD 字段变更、配置项废弃、依赖版本冲突
   - 输出：兼容性报告（不兼容项列表 + 影响范围 + 建议处理方式）

2. **人工核对层**：
   - 运维人员基于自动扫描报告进行人工复核
   - 针对业务相关的不兼容项进行评估与决策
   - 确认升级路径的可行性
