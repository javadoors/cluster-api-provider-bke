## 一、openFuyao 平台整体规划介绍

openFuyao 社区向工行团队介绍了平台的整体架构与演进规划，重点阐述了两大核心建设主线：

### 1.1 声明式升级框架

openFuyao 正在构建企业级声明式升级框架，实现集群全生命周期的自动化管理。该框架基于 DAG（有向无环图）编排引擎，支持组件依赖管理、并行执行优化和断点续传能力。

**核心特性**：
- **声明式 API**：通过 `ComponentVersion` CRD 声明组件版本与依赖关系
- **多类型组件支持**：统一支持 binary（二进制）、helm（Chart）、yaml（清单）、inline（内联）四种组件类型
- **三层状态机**：集群级、节点级、组件级分层状态管理，精确控制升级流程
- **可观测性**：升级进度实时展示、状态查询、事件日志、指标监控四大能力

### 1.2 核心组件 Operator 化

参考 OpenShift CVO（Cluster Version Operator）架构，openFuyao 规划将核心组件改造为 Operator 模式，实现声明式版本收敛。

**规划范围**：
- **版本管理 Operator（CVO）**：管理集群版本生命周期，协调所有 Operator 升级
- **基础设施 Operator**：网络（CNO）、存储（CSO）、DNS、Ingress 等
- **K8s 核心组件 Operator**：API Server、Controller Manager、Scheduler、etcd
- **扩展 Operator**：监控、认证、备份等

## 二、工行节点级运维能力开发进展

工行团队介绍了当前正在开发的节点级运维能力模块，主要包括：

- 节点环境初始化（内核参数、容器运行时、网络配置等）
- 节点健康检查与故障自愈
- 节点配置管理与版本控制

**关键议题**：工行当前的二进制组件安装方案基于硬编码逻辑实现，与 openFuyao 最新的声明式升级框架设计存在差异。双方达成共识，工行需结合 openFuyao 声明式框架重新调整二进制组件的安装方案，确保技术路线一致性。

**调整方向**：
- 将硬编码的安装逻辑迁移至 `ComponentVersion` CRD 声明式配置
- 复用 openFuyao 的 `BinaryInstaller` 组件，统一二进制组件的安装/升级/卸载流程
- 对齐三层状态机模型，确保节点级状态与集群级状态协同

## 五、技术议题讨论

### 5.1 升级兼容性工具

**背景**：跨版本升级时，需识别 API 变更、配置变更、依赖变更等兼容性问题。

**讨论结论**：

升级兼容性检查应采用"**自动扫描 + 人工核对**"的双层机制：

1. **自动扫描层**：
   - 开发兼容性扫描工具，基于版本差异自动识别不兼容点
   - 扫描范围：API 版本变更、CRD 字段变更、配置项废弃、依赖版本冲突
   - 输出：兼容性报告（不兼容项列表 + 影响范围 + 建议处理方式）

2. **人工核对层**：
   - 运维人员基于自动扫描报告进行人工复核
   - 针对业务相关的不兼容项进行评估与决策
   - 确认升级路径的可行性

**工具设计方向**：
- 输入：当前版本 + 目标版本
- 处理：解析两个版本的 ReleaseImage，对比组件清单、API 定义、配置项
- 输出：兼容性报告（JSON/HTML 格式）
