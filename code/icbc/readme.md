# openFuyao 与工行合作开发讨论方案

## 一、背景与目标

### 1.1 背景

openFuyao 是一个基于 Kubernetes 的云原生平台，提供完整的集群生命周期管理能力。当前 openFuyao 已规划：

- **声明式升级框架**：基于 DAG 的组件依赖编排
- **版本管理机制**：参考 OpenShift CVO 的版本管理 Operator
- **备份恢复体系**：etcd 备份、配置备份、应用数据备份

工行希望基于 openFuyao 平台，构建符合金融行业要求的版本管理和备份恢复能力。

### 1.2 合作目标

通过本次合作，实现以下目标：

1. **构建企业级声明式升级框架**，实现自动化的版本管理
2. **参考 OpenShift CVO 机制**，构建版本管理 Operator，实现声明式版本管理
3. **构建企业级备份与恢复体系**，保障平台数据安全和业务连续性
4. **形成可复用的合作模式**，为后续合作奠定基础

## 二、合作特性一：声明式升级框架

### 2.1 合作目标

构建企业级声明式升级框架，实现 openFuyao 平台自动化的版本管理能力。

### 2.2 核心能力

#### 2.2.1 统一升级框架

基于 DAG（有向无环图）的组件依赖编排，支持管理集群和业务集群统一升级。

**核心特性**：
- **组件依赖管理**：通过 `ComponentVersion` CRD 声明组件间依赖关系
- **拓扑排序执行**：自动计算组件执行顺序，确保依赖关系正确
- **并行执行优化**：无依赖组件可并行执行，提高升级效率

**技术实现**：
```yaml
# 组件依赖声明示例
apiVersion: config.openfuyao.cn/v1alpha1
kind: ComponentVersion
metadata:
  name: install-service
spec:
  version: "26.06"
  dependencies:
    - name: provider  # provider 必须先完成
```

#### 2.2.2 版本路径管理

通过 `UpgradePath` CRD 定义合法升级路径，自动验证路径合法性。

**核心特性**：
- **路径验证**：升级前自动验证路径是否在合法路径中
- **多跳升级**：支持跨多个版本的升级，自动计算最短路径
- **LTS 版本支持**：支持长期支持版本的升级策略

**升级路径示例**：
```
相邻版本升级：26.03 → 26.06 → 26.09 → 26.12
LTS 版本升级：25.12 → 26.12 → 27.12
```

#### 2.2.3 ReleaseImage 规范

使用 OCI 镜像作为版本载体，声明组件清单和依赖关系。

**核心特性**：
- **标准化打包**：所有组件打包成标准 OCI 镜像
- **组件清单**：明确声明版本包含的组件及其版本
- **依赖声明**：声明组件间的依赖关系
- **签名验证**：支持镜像签名验证，确保安全性

**ReleaseImage 结构**：
```yaml
apiVersion: config.openfuyao.cn/v1alpha1
kind: ReleaseImage
metadata:
  name: openfuyao-v26.06
spec:
  version: "26.06"
  components:
    - name: provider
      version: "26.06"
      image: "registry.openfuyao.cn/provider:26.06"
    - name: install-service
      version: "26.06"
      image: "registry.openfuyao.cn/install-service:26.06"
      dependencies:
        - provider
```

#### 2.2.4 升级前预检（Pre-Check）

升级前自动执行预检，确保升级条件满足。

**预检项目**：
| 检查项 | 说明 | 失败处理 |
|--------|------|---------|
| 集群健康检查 | 检查节点、etcd、控制面组件状态 | 阻止升级 |
| 备份验证 | 验证 etcd 快照、配置备份是否可用 | 阻止升级 |
| 路径验证 | 验证升级路径是否合法 | 阻止升级 |
| 资源检查 | 检查磁盘、内存、CPU 是否充足 | 阻止升级 |

#### 2.2.5 升级后验证（Post-Upgrade）

升级后自动执行验证，确保升级成功。

**验证项目**：
| 验证项 | 说明 | 失败处理 |
|--------|------|---------|
| 组件版本验证 | 验证所有组件版本是否一致 | 告警通知 |
| 集群健康验证 | 验证集群各组件健康状态 | 告警通知 |
| 业务应用验证 | 验证关键业务应用是否正常 | 告警通知 |

### 2.3 合作价值

| 价值点 | 说明 |
|--------|------|
| **自动化升级** | 减少人工干预，降低升级风险 |
| **可观测性** | 完整的升级状态跟踪和日志记录 |
| **可复用** | 工行可复用框架升级自有组件 |

## 三、合作特性二：Operator 化（参考 OpenShift CVO）

### 3.1 合作目标

参考 OpenShift CVO（Cluster Version Operator）机制，构建 openFuyao 的版本管理 Operator，实现声明式版本管理。

### 3.2 核心能力

#### 3.2.1 ClusterVersion Operator

版本生命周期管理，声明式版本管理。

**核心特性**：
- **声明式 API**：用户设置 `spec.desiredVersion`，系统自动收敛到目标版本
- **状态跟踪**：通过 `ClusterVersion` CRD 跟踪当前版本、目标版本、升级历史
- **自动协调**：自动检测版本差异，触发升级/降级流程
- **历史记录**：记录完整的升级/降级历史，支持审计

**ClusterVersion CRD**：
```yaml
apiVersion: config.openfuyao.cn/v1alpha1
kind: ClusterVersion
metadata:
  name: version
spec:
  desiredVersion: "26.06"  # 目标版本
status:
  currentVersion: "26.03"  # 当前版本
  phase: "Upgrading"       # 当前状态
  history:
    - state: "Completed"
      version: "26.03"
      completionTime: "2026-01-15T10:00:00Z"
    - state: "Partial"
      version: "26.06"
      startedTime: "2026-02-10T09:00:00Z"
```

#### 3.2.2 版本降级能力

支持版本降级（OpenShift 不支持），作为差异化能力。

**与 OpenShift 对比**：
| 能力 | OpenShift | openFuyao |
|------|-----------|-----------|
| 版本降级 | ❌ 不支持 | ✅ 支持 |
| 自动回滚 | ❌ 不支持 | ✅ 可设计 |
| 升级失败处理 | 联系支持/etcd 恢复 | 降级 + etcd 恢复 |

#### 3.2.3 自动回滚机制

升级失败可自动触发回滚（OpenShift 不支持）。

**回滚策略**：
```
升级失败
  ↓
自动检测失败原因
  ↓
├─ 瞬时故障 → 自动重试（最多 3 次）
├─ 可恢复错误 → 自动回滚到上一版本
└─ 不可恢复错误 → 告警通知，等待人工介入
```

### 3.3 合作价值

| 价值点 | 说明 |
|--------|------|
| **声明式管理** | 简化版本管理，降低运维复杂度 |
| **版本降级** | OpenShift 不支持的差异化能力 |
| **自动回滚** | 减少人工干预，提高恢复速度 |

## 四、合作特性三：备份与恢复

### 4.1 合作目标

构建企业级备份与恢复体系，保障 openFuyao 平台数据安全和业务连续性。

### 4.2 核心能力

#### 4.2.1 etcd 自动备份

每日自动备份 etcd，支持手动备份。

**备份策略**：
| 备份类型 | 频率 | 保留周期 | 存储位置 |
|---------|------|---------|---------|
| 自动备份 | 每日凌晨 2 点 | 7 天 | 本地 + 远程 |
| 手动备份 | 升级前触发 | 30 天 | 本地 + 远程 |

**备份内容**：
- etcd 完整数据快照
- 集群配置（BKECluster、BKENode 等）
- 证书和密钥

#### 4.2.2 配置备份

备份集群配置，支持配置恢复。

**备份内容**：
| 配置类型 | 说明 |
|---------|------|
| BKECluster CRD | 集群配置 |
| BKENode CRD | 节点配置 |
| ConfigMap | 配置映射 |
| Secret | 密钥信息 |

#### 4.2.3 应用数据备份

集成 Velero，支持应用数据和 PVC 数据备份。

**备份能力**：
| 能力 | 说明 |
|------|------|
| 应用数据备份 | 备份 Deployment、StatefulSet 等应用数据 |
| PVC 数据备份 | 备份持久卷数据 |
| 定时备份 | 支持 CronJob 定时备份 |
| 增量备份 | 支持增量备份，减少存储空间 |

#### 4.2.4 双副本存储

本地（7天）+ 远程（30天）双副本存储。

**存储架构**：
```
┌─────────────────────────────────────────────────────────────┐
│                    备份存储架构                              │
└─────────────────────────────────────────────────────────────┘

┌──────────────┐
│  openFuyao   │
│    集群      │
└──────┬───────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────┐
│  L1: 本地存储（/backup）                                      │
│  ├─ etcd/          (etcd 快照)                               │
│  ├─ config/        (集群配置)                                │
│  ├─ velero/        (应用数据)                                │
│  └─ 保留策略: 7 天                                           │
└──────────────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────────┐
│  L2: 远程存储（工行提供）                                     │
│  ├─ S3 兼容存储（推荐）                                       │
│  ├─ NFS 存储                                                 │
│  └─ 保留策略: 30 天                                           │
└──────────────────────────────────────────────────────────────┘
```

#### 4.2.5 备份验证

定期自动验证备份可恢复性。

**验证策略**：
| 验证类型 | 频率 | 说明 |
|---------|------|------|
| 自动验证 | 每周日凌晨 3 点 | 自动恢复备份到测试环境验证 |
| 手动验证 | 升级前 | 手动验证备份可恢复性 |

**验证内容**：
- etcd 数据完整性验证
- 配置正确性验证
- 应用数据可用性验证

### 4.3 合作价值

| 价值点 | 说明 |
|--------|------|
| **数据安全** | 完整的备份体系，保障数据安全 |
| **业务连续** | 快速恢复能力，保障业务连续性 |
| **合规要求** | 满足金融行业合规要求 |
| **双副本存储** | 防止单点故障，提高可靠性 |
| **自动验证** | 确保备份有效性 |

## 七、风险与应对

### 7.1 技术风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 升级框架复杂度高 | 开发周期延长 | 分阶段开发，优先核心功能 |
| 版本降级实现困难 | 降级能力无法实现 | 先实现简单方案，后续优化 |
| 备份数据量大 | 存储成本高 | 采用增量备份，优化存储策略 |

### 7.2 协作风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 需求变更频繁 | 开发进度受影响 | 建立需求变更流程，控制变更范围 |
| 沟通不畅 | 理解偏差 | 定期沟通会议，建立沟通机制 |
| 资源不足 | 交付延期 | 提前规划资源，确保资源到位 |
