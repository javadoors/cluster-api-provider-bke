# openFuyao 与工行合作开发讨论方案

## 一、背景与目标

### 1.1 背景

openFuyao 是一个基于 Kubernetes 的云原生平台，提供完整的集群生命周期管理能力。当前 openFuyao 已规划：

- **声明式升级框架**：基于 DAG 的组件依赖编排
- **版本管理机制**：参考 OpenShift CVO 的版本管理 Operator
- **备份恢复体系**：etcd 备份、配置备份、应用数据备份

工行希望基于 openFuyao 平台，构建符合金融行业要求的版本管理和备份恢复能力。

### 1.2 合作目标

通过本次合作，实现以下目标：

1. **构建企业级声明式升级框架**，实现自动化、可观测、可回滚的版本管理
2. **参考 OpenShift CVO 机制**，构建版本管理 Operator，实现声明式版本收敛
3. **构建企业级备份与恢复体系**，保障平台数据安全和业务连续性
4. **形成可复用的合作模式**，为后续合作奠定基础

## 二、合作特性一：声明式升级框架

### 2.1 合作目标

构建企业级声明式升级框架，实现 openFuyao 平台的自动化、可观测、可回滚的版本管理能力。

### 2.2 核心能力

#### 2.2.1 统一升级框架

基于 DAG（有向无环图）的组件依赖编排，支持管理集群和业务集群统一升级。

**核心特性**：
- **组件依赖管理**：通过 `ComponentVersion` CRD 声明组件间依赖关系
- **拓扑排序执行**：自动计算组件执行顺序，确保依赖关系正确
- **并行执行优化**：无依赖组件可并行执行，提高升级效率

**技术实现**：
```yaml
# 组件依赖声明示例
apiVersion: config.openfuyao.cn/v1alpha1
kind: ComponentVersion
metadata:
  name: install-service
spec:
  version: "26.06"
  dependencies:
    - name: provider  # provider 必须先完成
```

#### 2.2.2 版本路径管理

通过 `UpgradePath` CRD 定义合法升级路径，自动验证路径合法性。

**核心特性**：
- **路径验证**：升级前自动验证路径是否在合法路径中
- **多跳升级**：支持跨多个版本的升级，自动计算最短路径
- **LTS 版本支持**：支持长期支持版本的升级策略

**升级路径示例**：
```
相邻版本升级：26.03 → 26.06 → 26.09 → 26.12
LTS 版本升级：25.12 → 26.12 → 27.12
```

#### 2.2.3 ReleaseImage 规范

使用 OCI 镜像作为版本载体，声明组件清单和依赖关系。

**核心特性**：
- **标准化打包**：所有组件打包成标准 OCI 镜像
- **组件清单**：明确声明版本包含的组件及其版本
- **依赖声明**：声明组件间的依赖关系
- **签名验证**：支持镜像签名验证，确保安全性

**ReleaseImage 结构**：
```yaml
apiVersion: config.openfuyao.cn/v1alpha1
kind: ReleaseImage
metadata:
  name: openfuyao-v26.06
spec:
  version: "26.06"
  components:
    - name: provider
      version: "26.06"
      image: "registry.openfuyao.cn/provider:26.06"
    - name: install-service
      version: "26.06"
      image: "registry.openfuyao.cn/install-service:26.06"
      dependencies:
        - provider
```

#### 2.2.4 升级前预检（Pre-Check）

升级前自动执行预检，确保升级条件满足。

**预检项目**：
| 检查项 | 说明 | 失败处理 |
|--------|------|---------|
| 集群健康检查 | 检查节点、etcd、控制面组件状态 | 阻止升级 |
| 备份验证 | 验证 etcd 快照、配置备份是否可用 | 阻止升级 |
| 路径验证 | 验证升级路径是否合法 | 阻止升级 |
| 资源检查 | 检查磁盘、内存、CPU 是否充足 | 阻止升级 |

#### 2.2.5 升级后验证（Post-Upgrade）

升级后自动执行验证，确保升级成功。

**验证项目**：
| 验证项 | 说明 | 失败处理 |
|--------|------|---------|
| 组件版本验证 | 验证所有组件版本是否一致 | 告警通知 |
| 集群健康验证 | 验证集群各组件健康状态 | 告警通知 |
| 业务应用验证 | 验证关键业务应用是否正常 | 告警通知 |

#### 2.2.6 声明式升级框架体系规划

基于现有升级框架和 BKE 的实际需求，规划以下升级框架体系：

**核心能力（P0 - 必须实现）**：

| 能力 | 职责 | 优先级 | 说明 |
|------|------|--------|------|
| **多类型组件支持** | 支持 inline/binary/helm/yaml 四种组件类型 | P0 | 统一升级框架，支持不同部署方式 |
| **三层状态机** | 集群/节点/组件三层状态管理、状态转换、状态持久化 | P0 | 精确控制升级流程，支持断点续传 |
| **可观测性** | 升级进度、状态查询、事件日志、指标监控 | P0 | 实时掌握升级状态，快速定位问题 |

**扩展能力（P1 - 推荐实现）**：

| 能力 | 职责 | 优先级 | 说明 |
|------|------|--------|------|
| **自升级组件** | install-service、provider 自升级 | P1 | 处理架构变更导致的自升级 |
| **升级回滚机制** | 自动回滚、手动回滚、版本降级 | P1 | 升级失败后的恢复能力 |

**多类型组件支持详解**：

| 组件类型 | 升级方式 | 适用场景 | 示例 |
|---------|---------|---------|------|
| **inline** | Go 代码处理器，直接执行升级逻辑 | 复杂升级逻辑、需要状态管理 | etcd 升级、Master 升级 |
| **binary** | 二进制文件升级，通过 Agent 分发执行 | 简单二进制升级、无需复杂逻辑 | BKE Agent 升级 |
| **helm** | Helm Chart 升级，支持 values 覆盖 | Helm 部署的应用、需要配置覆盖 | 监控组件、日志组件 |
| **yaml** | Kubernetes YAML 资源升级，支持 kubectl apply | 简单 K8s 资源升级 | ConfigMap、Secret、Deployment |

**三层状态机模型**：

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：集群级状态机（ClusterUpgrade）                       │
│  职责：协调整个升级流程，管理批次执行顺序                      │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  第二层：节点级状态机（NodeUpgrade）                          │
│  职责：管理单个节点的升级状态，协调节点上组件的升级             │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  第三层：组件级状态机（ComponentUpgrade）                     │
│  职责：执行具体的升级逻辑（inline/binary/helm/yaml）         │
└─────────────────────────────────────────────────────────────┘
```

**三层状态机设计原因**：

| 设计维度 | 设计原因 | 解决的问题 |
|---------|---------|-----------|
| **关注点分离** | 集群/节点/组件三个层级职责不同，分层后各层可独立演进 | 避免单体状态机过于复杂，降低理解和维护成本 |
| **故障隔离** | 单节点升级失败不影响其他节点，单组件失败可独立重试/回滚 | 防止局部故障扩散到整个集群，提高升级韧性 |
| **并行执行** | 集群级协调批次，节点级协调组件，无依赖组件可并行 | 百节点升级从串行数小时缩短到并行30分钟内 |
| **可观测性** | 每层独立状态+事件日志，可精确定位故障层级和组件 | 故障排查从"猜"变为"精确制导"，排查时间降低90% |
| **回滚粒度** | 支持组件级回滚、节点级回滚、集群级回滚三种粒度 | 根据故障范围选择最小回滚粒度，减少业务影响 |
| **扩展性** | 新增组件只需实现组件级状态机，无需修改集群/节点层 | 新组件接入开发时间从1周缩短到1天 |

```
三层状态机的优势：
┌─────────────────────────────────────────────────────────────────┐
│  L1 集群级: Upgrading (批次=3)                                   │
│       │                                                          │
│       ├─ L2 节点级 Master01: Upgrading                          │
│       │    ├─ L3 组件级 kubelet: Completed                       │
│       │    ├─ L3 组件级 apiserver: Running ← 当前               │
│       │    └─ L3 组件级 etcd: Pending                            │
│       │                                                          │
│       ├─ L2 节点级 Master02: Pending                            │
│       └─ L2 节点级 Master03: Pending                            │
│                                                                  │
│  优势:                                                           │
│  1. 状态清晰: 集群/节点/组件三层状态一目了然                       │
│  2. 可并行: 同一批次内节点可并行升级                              │
│  3. 故障隔离: Master01 组件失败不影响 Master02/03                 │
└─────────────────────────────────────────────────────────────────┘
```

**可观测性详解**：

| 能力 | 说明 |
|------|------|
| **升级进度** | 实时展示当前组件、已完成组件、待执行组件 |
| **状态查询** | 查询升级状态、组件状态、错误信息 |
| **事件日志** | 记录升级开始、组件升级、升级完成等事件 |
| **指标监控** | 升级耗时、成功率、失败原因等指标 |

```
┌─────────────────────────────────────────────────────────────────┐
│  3. 升级路径验证                                                  │
│     26.03 → 26.06 (合法路径 ✓)                                   │
│     预检: 集群健康 / 备份可用 / 资源充足                            │
└─────────────────────────────┬───────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. DAG 拓扑排序，计算执行顺序                                     │
│     Phase 1: Provider Self-Upgrade (P0)                          │
│     Phase 2: Agent Upgrade (P0)                                  │
│     Phase 3: Containerd Upgrade (P0)                             │
│     Phase 4: Etcd Upgrade (P0)                                   │
│     Phase 5: Master Upgrade (P0, 滚动)                           │
│     Phase 6: Worker Upgrade (P0, 滚动)                           │
│     Phase 7: Component Upgrade (P1)                              │
└─────────────────────────────┬───────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  5. 三层状态机驱动执行                                          │
│     L1 集群级: Initializing → Upgrading → Running               │
│     L2 节点级: Ready → Upgrading → Ready                        │
│     L3 组件级: Pending → Running → Completed                    │
└─────────────────────────────┬───────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  6. 升级后验证                                                  │
│     组件版本一致性 / 集群健康 / 业务应用正常                    │
│     更新 status.currentVersion = "26.06"                        │
│     记录升级历史                                                │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.2.1 ClusterVersion Operator

版本生命周期管理，声明式版本收敛。

**核心特性**：
- **声明式 API**：用户设置 `spec.desiredVersion`，系统自动收敛到目标版本
- **状态跟踪**：通过 `ClusterVersion` CRD 跟踪当前版本、目标版本、升级历史
- **自动协调**：自动检测版本差异，触发升级/降级流程
- **历史记录**：记录完整的升级/降级历史，支持审计

**ClusterVersion CRD**：
```yaml
apiVersion: config.openfuyao.cn/v1alpha1
kind: ClusterVersion
metadata:
  name: version
spec:
  desiredVersion: "26.06"  # 目标版本
status:
  currentVersion: "26.03"  # 当前版本
  phase: "Upgrading"       # 当前状态
  history:
    - state: "Completed"
      version: "26.03"
      completionTime: "2026-01-15T10:00:00Z"
    - state: "Partial"
      version: "26.06"
      startedTime: "2026-02-10T09:00:00Z"
```

#### 3.2.2 版本降级能力

支持版本降级（OpenShift 不支持），作为差异化能力。

**与 OpenShift 对比**：
| 能力 | OpenShift | openFuyao |
|------|-----------|-----------|
| 版本降级 | ❌ 不支持 | ✅ 支持 |
| 自动回滚 | ❌ 不支持 | ✅ 可设计 |
| 升级失败处理 | 联系支持/etcd 恢复 | 降级 + etcd 恢复 |

**降级方案**：
| 方案 | 实现方式 | 优点 | 缺点 | 
|------|---------|------|------|
| 方案一：复用升级流程 | 设置目标版本为旧版本，复用部署逻辑 | 实现简单、快速交付 | 可能需要更长时间 | 
| 方案二：降级 DAG | 专门的降级 DAG，按相反顺序降级 | 精确控制、可处理数据格式变更 | 实现复杂 | 

#### 3.2.3 自动回滚机制

升级失败可自动触发回滚（OpenShift 不支持）。

**回滚策略**：
```
升级失败
  ↓
自动检测失败原因
  ↓
├─ 瞬时故障 → 自动重试（最多 3 次）
├─ 可恢复错误 → 自动回滚到上一版本
└─ 不可恢复错误 → 告警通知，等待人工介入
```

## 四、合作特性三：备份与恢复

### 4.1 合作目标

### 4.2 核心能力

#### 4.2.1 etcd 自动备份

每日自动备份 etcd，支持手动备份。

**备份策略**：
| 备份类型 | 频率 | 保留周期 | 存储位置 |
|---------|------|---------|---------|
| 自动备份 | 每日凌晨 2 点 | 7 天 | 本地 + 远程 |
| 手动备份 | 升级前触发 | 30 天 | 本地 + 远程 |

**备份内容**：
- etcd 完整数据快照
- 集群配置（BKECluster、BKENode 等）
- 证书和密钥

#### 4.2.2 配置备份

备份集群配置，支持配置恢复。

**备份内容**：
| 配置类型 | 说明 |
|---------|------|
| BKECluster CRD | 集群配置 |
| BKENode CRD | 节点配置 |
| ConfigMap | 配置映射 |
| Secret | 密钥信息 |

#### 4.2.3 应用数据备份

集成 Velero，支持应用数据和 PVC 数据备份。

**备份能力**：
| 能力 | 说明 |
|------|------|

| PVC 数据备份 | 备份持久卷数据 |
| 定时备份 | 支持 CronJob 定时备份 |
| 增量备份 | 支持增量备份，减少存储空间 |

#### 4.2.4 双副本存储
