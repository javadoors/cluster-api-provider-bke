# BKE 回滚与备份能力规划（领导汇报版）

## 执行摘要

本规划为 BKE 平台构建完整的回滚与备份能力，参考 OpenShift 企业级最佳实践，结合 BKE 双机制架构（PhaseFlow + ClusterVersion）特点，实现**升级自动回滚、操作失败恢复、数据定期备份、灾难快速恢复**四大核心能力。项目从2026年Q4启动，分4个季度实施，总工作量 **17.5 人月**，确保平台具备生产级可靠性。

---

## 一、现状与问题

### 1.1 当前能力现状

**关键发现：BKE 当前没有任何自动化回滚能力**

| 机制 | 回滚能力 | 失败处理方式 |
|------|---------|-------------|
| **PhaseFlow** | ❌ 无 | 设置 `*Failed` 状态，需人工介入 |
| **ClusterVersion** | ❌ 无 | 设置 `Failed` 状态，需人工介入 |
| **声明式 DAG** | ❌ 无 | 记录错误，需人工介入 |

**核心问题**：
- 升级/扩缩容/配置变更失败后，只能手动重试或人工恢复
- 缺乏自动回滚机制，业务中断时间长
- 没有定期备份机制，数据丢失风险高
- 灾难恢复流程不完善，恢复时间长

### 1.2 BKE 双机制架构

BKE 采用双机制架构管理集群生命周期：

- **PhaseFlow**：负责操作类任务（安装、扩缩容、删除、纳管）
- **ClusterVersion**：负责版本生命周期管理（升级路径验证、镜像管理）
- **声明式 DAG**：负责执行升级/降级操作

回滚能力需要基于这两套机制分别设计，确保与现有架构兼容。

## 二、openFuyao 版本升级策略

### 2.1 设计思路

BKE 作为 openFuyao 平台的核心组件，其版本升级策略需要与 openFuyao 保持一致，确保：

1. **版本同步**：BKE 版本与 openFuyao 版本对齐，确保兼容性
2. **升级路径清晰**：提供明确的升级路径，降低升级风险
3. **稳定性保障**：通过 LTS 版本为生产环境提供长期支持
4. **回滚能力匹配**：回滚能力需要支持版本升级策略，确保升级失败可回滚

### 2.2 版本命名规范

- **格式**：`YY.MM`（年份后两位 + 月份）
- **示例**：`25.12`、`26.03`、`26.06`、`26.09`、`26.12`

### 2.3 版本发布周期

**每季度发布一个版本**：

| 季度 | 发布月份 | 版本示例 |
|------|---------|---------|
| Q1 | 3月 | 26.03 |
| Q2 | 6月 | 26.06 |
| Q3 | 9月 | 26.09 |
| Q4 | 12月 | 26.12 |

### 2.4 LTS 版本策略

- **每年最后一个版本（12月）为 LTS（长期支持）版本**
- 示例：25.12、26.12、27.12 均为 LTS 版本
- LTS 版本提供更长期的支持，适合生产环境

### 2.5 升级路径

**路径一：相邻版本升级**
```
26.03 → 26.06 → 26.09 → 26.12
```
- 升级间隔短（3个月）
- 变更较小，风险较低
- 适合追求新特性的用户

**路径二：LTS 版本升级**
```
25.12 → 26.12 → 27.12
```
- 升级间隔长（12个月）
- 变更较大，需充分测试
- 适合追求稳定性的生产环境用户

### 2.6 版本支持策略

| 版本类型 | 发布周期 | 支持周期 |
|---------|---------|---------|
| 标准版本 | 每季度 | 短期支持 |
| LTS 版本 | 每年12月 | 长期支持 |

### 2.7 与 BKE 版本对齐

- BKE 版本与 openFuyao 版本保持同步
- BKE 版本发布时，明确声明依赖的 openFuyao 版本
- 提供兼容性矩阵，说明版本间兼容性

## 三、核心能力规划

### 3.1 回滚能力

**PhaseFlow 回滚（操作类回滚）**：
- 扩缩容失败回滚：清理失败资源，恢复节点池
- 配置变更失败回滚：恢复配置文件，重启组件
- 安装失败处理：提供清理脚本，支持重建

**ClusterVersion 回滚（版本回滚）**：
- **方案一（推荐）**：重新部署旧版本（OpenShift 方式）
  - 复用现有部署逻辑，重新部署旧版本 ReleaseImage
  - 实现简单，工作量小，快速交付
- **方案二（增强）**：降级 DAG
  - 为每个组件实现特定的降级逻辑
  - 按相反顺序降级组件（Worker → Master → etcd → Containerd → Agent）
  - 处理复杂场景（如 etcd 数据格式变更）

### 3.2 备份能力

| 备份类型 | 备份频率 | 保留周期 | 方案 |
|---------|---------|---------|------|
| **etcd 数据** | 每日自动 | 7天 | etcdctl snapshot |
| **集群配置** | 变更时手动 | 7天 | 自定义脚本 |
| **证书和密钥** | 变更时手动 | 7天 | 自定义脚本 |
| **应用数据** | 每日自动 | 7天 | Velero |

### 3.3 恢复能力

| 恢复场景 | 恢复策略 | 预计恢复时间 |
|---------|---------|-------------|
| **单节点故障** | 自动替换节点 | 10-30 分钟 |
| **控制面故障** | 从备份恢复 etcd | 30-60 分钟 |
| **整个集群故障** | 重建集群 + 恢复数据 | 2-4 小时 |
| **数据丢失** | 从备份恢复数据 | 1-2 小时 |

## 四、各组件回滚方案

### 4.1 组件清单与回滚方案

| 组件 | 回滚方案 | 复杂度 | 工作量(人月) |
|------|---------|--------|-------------|
| **BKE Agent** | SSH 重新推送旧版本二进制 + 重启服务 | 简单 | 0.2 |
| **证书和密钥** | 从备份恢复 PKI 目录 | 简单 | 0.1 |
| **Containerd** | 重置 + 重新部署旧版本 | 中等 | 0.3 |
| **Master 组件** | 停止静态 Pod → 替换二进制/清单 → 重启 | 中等 | 0.5 |
| **Worker 组件** | 驱逐 Pod → 停止 kubelet → 替换二进制 → 重启 | 中等 | 0.3 |
| **etcd** | 恢复快照 + 降级二进制 | **复杂** | 0.6 |
| **配置** | 从备份恢复 ConfigMap/Secret | 中等 | 0.3 |
| **DAG 编排器** | 反向拓扑排序执行 | **复杂** | 0.5 |

### 4.2 回滚顺序（反向拓扑）

```
升级顺序：
pre-upgrade-resources → bkeagent + containerd → etcd → master → worker → kube-proxy + coredns

回滚顺序（反向）：
kube-proxy + coredns → worker → master → etcd → bkeagent + containerd → pre-upgrade-resources
```

### 4.3 兼容性约束

| 约束 | 说明 |
|------|------|
| **Kubernetes 版本倾斜** | kubelet 可以与 API Server 相差 ±1 个小版本 |
| **etcd 兼容性** | etcd 数据格式可能在不同版本间变化；回滚需要快照 |
| **Containerd CRI** | CRI API 在 containerd 和 kubelet 之间需要兼容 |
| **证书有效性** | 证书必须对所有组件有效 |
