# BKE 回滚与备份能力规划（领导汇报版）

## 执行摘要

本规划为 BKE 平台构建完整的回滚与备份能力，参考 OpenShift 企业级最佳实践，结合 BKE 双机制架构（PhaseFlow + ClusterVersion）特点，实现**升级降级能力、操作失败恢复、数据定期备份、灾难快速恢复**四大核心能力。项目从2026年Q4启动，分4个季度实施，总工作量 **17.5 人月**，确保平台具备生产级可靠性。

**重要说明**：OpenShift 不支持版本回滚。BKE 的降级能力是 BKE 的差异化能力设计。

## 一、现状与问题

### 1.1 当前能力现状

**关键发现：BKE 当前没有任何自动化回滚能力**

| 机制 | 回滚能力 | 失败处理方式 |
|------|---------|-------------|
| **PhaseFlow** | ❌ 无 | 设置 `*Failed` 状态，需人工介入 |
| **ClusterVersion** | ❌ 无 | 设置 `Failed` 状态，需人工介入 |
| **声明式 DAG** | ❌ 无 | 记录错误，需人工介入 |

**核心问题**：
- 升级/扩缩容/配置变更失败后，只能手动重试或人工恢复
- 缺乏自动回滚机制，业务中断时间长
- 没有定期备份机制，数据丢失风险高
- 灾难恢复流程不完善，恢复时间长

### 1.2 BKE 双机制架构

BKE 采用双机制架构管理集群生命周期：

- **PhaseFlow**：负责操作类任务（安装、扩缩容、删除、纳管）
- **ClusterVersion**：负责版本生命周期管理（升级路径验证、镜像管理）
- **声明式 DAG**：负责执行升级/降级操作

回滚能力需要基于这两套机制分别设计，确保与现有架构兼容。

## 二、OpenShift 洞察

### 2.1 OpenShift 回滚机制洞察

#### 2.1.1 安装回滚

**关键洞察**：OpenShift 安装过程**不支持自动回滚**

| 因素 | 说明 |
|------|------|
| **状态不可逆** | etcd 数据、证书、网络配置一旦创建无法简单回滚 |
| **基础设施耦合** | 云资源（VM、网络、存储）已创建 |
| **时间窗口** | 安装失败通常在早期阶段，重建比回滚更快 |

**推荐做法**：安装失败时销毁集群重新安装，而非尝试回滚。

#### 2.1.2 升级失败处理

**关键事实**：OpenShift **不支持将集群还原到以前版本**

根据 Red Hat 官方文档，OpenShift 升级是单向操作，不支持版本回滚。

**OpenShift 升级失败后的处理方式**：

| 方式 | 说明 |
|------|------|
| **联系 Red Hat 支持** | 提交支持工单，获取专业指导 |
| **从 etcd 备份恢复** | 如果有 etcd 备份，可以恢复到备份时的状态 |
| **重建集群** | 如果无法从备份恢复，需要重建集群 |

**为什么 OpenShift 不支持回滚？**

1. **数据格式变更不可逆**：升级过程中 etcd 数据格式可能发生变化
2. **组件版本依赖复杂**：多个 Operator 之间存在复杂的版本依赖关系
3. **状态一致性难以保证**：回滚可能导致集群状态不一致
4. **测试覆盖困难**：回滚路径的测试矩阵过于庞大

**BKE 的差异化能力**：

BKE 计划实现版本降级能力，作为与 OpenShift 的差异化能力：
- 支持用户手动触发降级到旧版本
- 通过声明式 DAG 执行降级操作
- 提供两种降级方案：降级 DAG 和复用升级流程

#### 2.1.3 扩容后的缩容

**支持声明式缩容**（注意：这是节点缩容，不是版本回滚）：
- 通过修改 `MachineDeployment` 的 `replicas` 字段触发缩容
- 缩容流程：减少副本数 → 删除多余 Machine → 销毁 VM → 移除节点
- 优雅删除：先 cordon → drain → delete
- 数据保留：PVC 数据可选择保留或删除

### 2.2 OpenShift 备份恢复洞察

#### 2.2.1 etcd 备份

- **备份方式**：`etcdctl snapshot save`
- **备份频率**：建议每日自动备份
- **保留周期**：建议保留 7 天
- **备份验证**：定期验证备份可恢复性

#### 2.2.2 应用数据备份

- **备份工具**：Velero（OpenShift API for Data Protection）
- **备份内容**：应用数据、PVC 数据、ConfigMap、Secret
- **备份策略**：支持定时备份和手动备份
- **存储位置**：支持 S3、NFS、OSS 等多种存储后端

#### 2.2.3 灾难恢复

| 故障场景 | 恢复策略 | 预计恢复时间 |
|---------|---------|-------------|
| **单节点故障** | 自动替换节点 | 10-30 分钟 |
| **控制面故障** | 从备份恢复 etcd | 30-60 分钟 |
| **整个集群故障** | 重建集群 + 恢复数据 | 2-4 小时 |
| **数据丢失** | 从备份恢复数据 | 1-2 小时 |

### 2.3 OpenShift 设计哲学洞察

#### 2.3.1 保守策略

- 安装不支持回滚：快速失败，重建集群
- 升级不支持回滚：升级失败后需联系支持或从备份恢复
- 对于复杂场景，推荐重建集群

#### 2.3.2 权衡取舍

| 方面 | 优点 | 缺点 |
|------|------|------|
| **重建集群** | 彻底解决问题 | 恢复时间长 |
| **从备份恢复** | 可恢复到已知状态 | 需要提前备份 |
| **联系支持** | 获取专业指导 | 响应时间长 |

#### 2.3.3 对 BKE 的启示

1. **安装失败**：采用 OpenShift 策略，快速失败，重建集群
2. **升级失败**：由于 OpenShift 不支持回滚，BKE 实现降级能力作为差异化能力
3. **始终**：提供从备份恢复的替代方案，作为最后手段

## 三、openFuyao 版本升级策略

### 3.1 设计思路

openFuyao采用统一的版本升级策略，确保：

1. **升级路径清晰**：提供明确的升级路径，降低升级风险
2. **稳定性保障**：通过 LTS 版本为生产环境提供长期支持
3. **回滚能力匹配**：回滚能力需要支持版本升级策略，确保升级失败可回滚

### 3.2 版本命名规范

- **格式**：`YY.MM`（年份后两位 + 月份）
- **示例**：`25.12`、`26.03`、`26.06`、`26.09`、`26.12`

### 3.3 版本发布周期

**每季度发布一个版本**：

| 季度 | 发布月份 | 版本示例 |
|------|---------|---------|
| Q1 | 3月 | 26.03 |
| Q2 | 6月 | 26.06 |
| Q3 | 9月 | 26.09 |
| Q4 | 12月 | 26.12 |

### 3.4 LTS 版本策略

- **每年最后一个版本（12月）为 LTS（长期支持）版本**
- 示例：25.12、26.12、27.12 均为 LTS 版本
- LTS 版本提供更长期的支持，适合生产环境

### 3.5 升级路径

**路径一：相邻版本升级**
```
26.03 → 26.06 → 26.09 → 26.12
```
- 升级间隔短（3个月）
- 变更较小，风险较低
- 适合追求新特性的用户

**路径二：LTS 版本升级**
```
25.12 → 26.12 → 27.12
```
- 升级间隔长（12个月）
- 变更较大，需充分测试
- 适合追求稳定性的生产环境用户

### 3.6 版本支持策略

| 版本类型 | 发布周期 | 支持周期 |
|---------|---------|---------|
| 标准版本 | 每季度 | 6 个月 |
| LTS 版本 | 每年12月 | 3 年 |

### 3.7 版本兼容性

- 提供兼容性矩阵，说明各版本间的兼容性关系

### 3.8 升级能力概述

#### 升级机制

BKE 采用 **ClusterVersion + 声明式 DAG** 双机制协作完成集群升级：

- **ClusterVersion**：负责版本生命周期管理（升级路径验证、ReleaseImage 拉取）
- **声明式 DAG**：负责按拓扑顺序执行组件升级（Agent → Containerd → etcd → Master → Worker）

#### 升级类型

| 升级类型 | 说明 | 示例 | 适用场景 |
|---------|------|------|---------|
| **相邻版本升级** | 升级到下一个季度版本 | 26.03 → 26.06 | 常规升级，变更较小 |
| **LTS 版本升级** | 升级到下一个 LTS 版本（逐跳） | 25.12 → 26.12 | 生产环境大版本升级 |
| **补丁升级** | 同一版本内的补丁更新 | 26.06.1 → 26.06.2 | 安全修复、Bug 修复 |

#### 升级流程（三阶段）

| 阶段 | 关键动作 | 通过条件 |
|------|---------|---------|
| **Pre-Check（预检）** | 集群健康检查、备份验证、路径验证、资源检查 | 所有检查项通过 |
| **升级执行** | 按 DAG 顺序逐组件升级，每组件升级后健康检查 | 所有组件升级成功 |
| **Post-Upgrade（升级后验证）** | 组件版本一致性、集群健康、业务应用验证 | 所有验证项通过 |

### 3.9 升级路径设计

#### UpgradePath CRD

UpgradePath CRD 定义合法的升级路径，包含起始版本（from）、目标版本（to）和约束条件。ClusterVersion Controller 在升级前验证路径合法性。

#### 升级路径

**路径一：相邻版本升级**
```
26.03 → 26.06 → 26.09 → 26.12
```
- 升级间隔短（3个月），变更较小，风险较低

**路径二：LTS 版本升级（逐跳）**
```
25.12 → 26.03 → 26.06 → 26.09 → 26.12 → 27.03 → ... → 27.12
```
- 不能跳过中间版本，每一跳变更较小

#### 路径验证规则

1. 目标版本必须在 UpgradePath CRD 中存在合法路径
2. 只能升级到相邻版本或逐跳升级到目标版本
3. 目标版本的 ReleaseImage 必须可用
4. 当前版本与目标版本之间不能有不可逆的数据格式变更

#### 兼容性矩阵

| 当前版本 | 可升级版本 | 说明 |
|---------|-----------|------|
| 26.03 | 26.06 | 相邻版本升级 |
| 26.06 | 26.09, 26.03（降级） | 相邻版本升级/降级 |
| 26.09 | 26.12, 26.06（降级） | 相邻版本升级/降级 |
| 26.12（LTS） | 27.03, 26.09（降级） | LTS 版本升级/降级 |
| 25.12（LTS） | 26.03, 26.12（LTS，需逐跳） | LTS 版本升级（逐跳） |

### 3.10 停机窗口分析

#### 各组件升级停机影响

| 组件 | 控制面影响 | 工作节点影响 | 业务应用影响 |
|------|-----------|-------------|-------------|
| **BKE Agent** | 无 | 无 | 无 |
| **Containerd** | 无 | 节点上容器短暂重启 | 该节点上的 Pod 短暂不可用 |
| **etcd** | etcd 逐个成员升级，集群仍可用 | 无直接影响 | API Server 可能短暂延迟增加 |
| **Master 组件** | API Server 逐个升级 | 无直接影响 | 多副本时 API 仍可用，单副本时短暂不可用 |
| **Worker 组件** | 无 | 逐个节点升级 | Pod 被驱逐后在其他节点重建 |

#### 停机时间最小化策略

1. **Pod 干扰预算（PDB）**：为关键业务应用配置 PDB，确保升级期间最小可用副本数
2. **滚动升级**：逐个组件升级，避免同时升级多个组件
3. **多副本部署**：Master 和 etcd 至少 3 节点，确保升级期间集群可用
4. **业务应用多副本**：关键业务应用配置多副本和反亲和性，避免单点故障
5. **维护窗口**：对于单副本控制面，建议在维护窗口期间升级

#### 停机窗口汇总

| 升级场景 | 控制面影响 | 业务影响 | 建议 |
|---------|-----------|---------|------|
| **多副本集群升级** | 无停机 | 无停机（滚动升级） | 正常升级 |
| **单副本集群升级** | 短暂不可用 | 短暂不可用 | 建议维护窗口 |
| **LTS 跨版本升级** | 多次短暂不可用 | 多次短暂不可用 | 建议维护窗口，充分测试 |

## 四、核心能力规划

### 4.1 回滚能力

**PhaseFlow 回滚（操作类回滚）**：
- 扩缩容失败回滚：清理失败资源，恢复节点池
- 配置变更失败回滚：恢复配置文件，重启组件
- 安装失败处理：提供清理脚本，支持重建

**ClusterVersion 降级（版本降级，BKE 差异化能力）**：
- **方案一（推荐）**：复用升级流程执行降级
   - 设置目标版本为旧版本，按正常升级流程反向执行
   - 实现简单，工作量小，快速交付
   - **注意**：OpenShift 不支持版本回滚，这是 BKE 的差异化能力
- **方案二（增强）**：降级 DAG
   - 为每个组件实现特定的降级逻辑
   - 按相反顺序降级组件（Worker → Master → etcd → Containerd → Agent）
   - 处理复杂场景（如 etcd 数据格式变更）

### 4.2 备份能力

| 备份类型 | 备份频率 | 保留周期 | 方案 |
|---------|---------|---------|------|
| **etcd 数据** | 每日自动 | 7天 | etcdctl snapshot |
| **集群配置** | 变更时手动 | 7天 | 自定义脚本 |
| **证书和密钥** | 变更时手动 | 7天 | 自定义脚本 |
| **应用数据** | 每日自动 | 7天 | Velero |

### 4.3 恢复能力

| 恢复场景 | 恢复策略 | 预计恢复时间 |
|---------|---------|-------------|
| **单节点故障** | 自动替换节点 | 10-30 分钟 |
| **控制面故障** | 从备份恢复 etcd | 30-60 分钟 |
| **整个集群故障** | 重建集群 + 恢复数据 | 2-4 小时 |
| **数据丢失** | 从备份恢复数据 | 1-2 小时 |

## 五、各组件降级方案

### 5.1 组件清单与降级方案

| 组件 | 降级方案 | 复杂度 | 工作量(人月) |
|------|---------|--------|-------------|
| **BKE Agent** | SSH 重新推送旧版本二进制 + 重启服务 | 简单 | 0.2 |
| **证书和密钥** | 从备份恢复 PKI 目录 | 简单 | 0.1 |
| **Containerd** | 重置 + 重新部署旧版本 | 中等 | 0.3 |
| **Master 组件** | 停止静态 Pod → 替换二进制/清单 → 重启 | 中等 | 0.5 |
| **Worker 组件** | 驱逐 Pod → 停止 kubelet → 替换二进制 → 重启 | 中等 | 0.3 |
| **etcd** | 恢复快照 + 降级二进制 | **复杂** | 0.6 |
| **配置** | 从备份恢复 ConfigMap/Secret | 中等 | 0.3 |
| **DAG 编排器** | 反向拓扑排序执行 | **复杂** | 0.5 |

### 5.2 降级顺序（反向拓扑）

```
升级顺序：
pre-upgrade-resources → bkeagent + containerd → etcd → master → worker → kube-proxy + coredns

降级顺序（反向）：
kube-proxy + coredns → worker → master → etcd → bkeagent + containerd → pre-upgrade-resources
```

### 5.3 兼容性约束

| 约束 | 说明 |
|------|------|
| **Kubernetes 版本倾斜** | kubelet 可以与 API Server 相差 ±1 个小版本 |
| **etcd 兼容性** | etcd 数据格式可能在不同版本间变化；降级需要快照 |
| **Containerd CRI** | CRI API 在 containerd 和 kubelet 之间需要兼容 |
| **证书有效性** | 证书必须对所有组件有效 |
